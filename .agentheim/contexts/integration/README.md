# Integration

## Purpose
**Adapters to external systems.** Translates external shapes (TMDB / RAWG / Steam / HLTB / Jellyfin) into commands the core BCs accept, and runs scheduled sync jobs that pull external state on a cadence. The anticorruption layer that keeps core BCs free of HTTP and vendor JSON.

## Classification
**generic** — Boring plumbing where boring choices are correct.

## Actors
External services (TMDB API, RAWG API, Steam Web API, HLTB scraping, Jellyfin server) and the single user (triggering manual refresh / sync actions).

## Ubiquitous language

- **Adapter** — module that owns one external system (`Tmdb.fs`, `Rawg.fs`, `Steam.fs`, `HowLongToBeat.fs`, `Jellyfin.fs`, `Qbittorrent.fs`). Translates DTOs ↔ domain language. `Steam.fs` has no SteamKit2 satellite anymore (integration-v0xmv, ADR-0070, 2026-09-05) — `SteamConnect.fs` (the one-time QR login, integration-hebjs/zwnh4) is deleted outright, and `Server.fsproj` carries no `SteamKit2`/`QRCoder` dependency; every Steam call in this BC is plain `HttpClient`.
- **Session (qBittorrent)** — `Qbittorrent.withSession` is deliberately login-once-use-once: it logs in exactly once per operation (`POST /api/v2/auth/login`, form `username`/`password`; a body of `Fails.` or an HTTP 403-banned-client response is `AuthFailed`, never a generic HTTP error), hands the caller a `Session` carrying the `SID` cookie, and sends it back as an explicit `Cookie: SID=…` request header on every subsequent call — no `Origin`/`Referer` header is ever added (qBittorrent's CSRF check only rejects cross-origin browsers). Unlike Jellyfin's `AccessToken`, the `SID` is never persisted and there is no re-auth-and-retry seam (ADR-0070 point 7): a qBittorrent session is cheap to reacquire, so `withSession` simply forgets it once the operation returns. `Qbittorrent.testConnection`/the Settings "Test connection" button use it read-only (`GET /api/v2/app/version` + `torrents/info` count); `deleteTorrents` (`POST /api/v2/torrents/delete`, `hashes` joined with `|`, `deleteFiles=true|false`) exists as a typed primitive here but integration-r4vzm is its first and only caller (integration-qb7tk).
- **External id** — TMDB id, RAWG id, Steam appId, Jellyfin item id. Stored on core aggregates so adapters can re-sync.
- **Throttle** — Adapter-owned minimum spacing between calls to one external endpoint family, because a vendor's rate ceiling is vendor knowledge; callers never pace themselves. `Steam.throttleStorefrontCall` (integration-w7ktb, ADR-0066) gates every `store.steampowered.com` storefront call (`appdetails`, trailers, search store-meta, and the Deck-compat store-page fetch) behind one process-wide gate — a `SemaphoreSlim` held for a call's full duration plus a minimum-interval wait (default 1500ms, derived from Steam's ~200 req/5min informal ceiling) — replacing eleven independently-remembered, caller-owned `Async.Sleep`s (three of which existed; eight of which didn't, including the Family import's per-app loop).

- **Import** — one-time pull of items from an external source into core BCs (e.g. a Steam library import becomes Games + play-time history).
- **Incremental import / diff, don't re-import** (integration-n3vqa) — the default Steam Family import shape: `GetSharedLibraryApps` (one call, unchanged) is diffed against `GameProjection.findBySteamAppId` before any per-app enrichment happens. A **known** app (an appId hit) still gets its family-owner/library-date commands but skips `getSteamStoreDetails` and every download entirely; a **new** app (no hit) still gets the full creation path. This is the fix for the burst-enumerate-everything traffic shape Valve twice flagged the builder's account over — the steady-state click costs a fixed, small, enumerable number of Steam requests (family group + shared library + owned-games-supplement) instead of one `appdetails` fetch per already-known title. An **arrival** is any app classified "what's new" — brand-new, or already-known but whose `rt_time_acquired` postdates the previous `steam_family_last_sync` (someone in the family buying a title the caller already owns is still news) — reported by name/acquired-date/adding-family-member in `SteamFamilyImportResult.Arrivals` and persisted whole (`steam_family_last_result`, JSON-in-SettingsStore, mirroring `steam_family_members`'s own pattern) so Settings can re-render "N new since ..." after a reload. Under ADR-0043 an arrival is cache-shaped (Steam's own description of when a title arrived, always re-fetchable from `GetSharedLibraryApps`) — it is never an event; `Games.Set_steam_library_date` already records the acquired date on the aggregate. **Full re-enrich** — an explicit second action (`/api/stream/reenrich-steam-family`, `Api.FullReenrich`) — reproduces the pre-n3vqa always-fetch-everything behaviour on demand; it is never the default click.
- **Sync** — repeating pull of external state. Two cadences exist: **scheduled** syncs run on a server timer (`ScheduledJobs.fs`: Steam library + play time, Series TMDB refresh), while the **Jellyfin** sync is *client-initiated* — triggered when the SPA loads, gated by a 5-minute cooldown and an in-progress lock in `JellyfinSync.fs` (not a `ScheduledJobs` job). The sync's last **result** (counts + error list / failure message) is persisted via `SettingsStore` so a breakage is visible across restarts, and any per-item failure surfaces as `JellyfinSyncStatus.SyncFailed` (integration-001). A Jellyfin fetch that returns **401/403** (a rejected token) triggers exactly one self-healing **re-auth**: the adapter re-authenticates with the stored `jellyfin_username`/`jellyfin_password`, persists the fresh `jellyfin_access_token` + `jellyfin_user_id`, and retries the failed request once; a second rejection, a failed re-auth, or missing credentials surface a clear "re-authentication" `SyncFailed` instead of looping (integration-002, `Jellyfin.withReauthRetry`).
- **Refresh token** — a long-lived credential (obtained via a one-time interactive login) from which an adapter mints short-lived **access tokens** on demand, so expiry never becomes user-facing manual work. The Jellyfin adapter does this with a username/password credential (see re-auth above, ADR-0011): a rejected `jellyfin_access_token` triggers one self-healing re-authentication via the stored `jellyfin_username`/`jellyfin_password`, persisting a fresh token and retrying once. **Steam Family has no refresh token or mint-and-retry seam** (integration-v0xmv, ADR-0070, 2026-09-05, superseding ADR-0061): the QR login that used to obtain one, and everything that minted access tokens from it, is deleted outright after a Valve permanent-ban threat traced to that login. Steam Family's `access_token` (`steam_family_token`, SettingsStore) is a short-lived, browser-obtained token the user pastes by hand — see **Manual token** below.
- **Manual token** (integration-v0xmv, ADR-0070) — Steam Family's only credential now: the user copies `webapi_token` from their own logged-in browser's `store.steampowered.com/pointssummary/ajaxgetasyncconfig` response and pastes it into Settings. Lasts roughly a day; a 401/403 from `IFamilyGroupsService` maps (`Steam.mapFamilyFetchError`) to a fixed `"family token rejected: "`-prefixed message, driving `SteamFamilyTokenRejected` and a "paste a fresh token" warning — no button anywhere performs a Steam login or mints a token on the user's behalf.
- **Refresh** — user-triggered re-fetch of a single item's metadata (e.g. "refresh this series from TMDB").
- **Materialize** — fill a metadata gap a primary source has not (yet) covered by writing rows from a *secondary* source, tagged with provenance so the primary source enriches them later. Today: when TMDB lags on a new season, the Jellyfin sync materializes the missing season/episode metadata from the user's Jellyfin server (`JellyfinImport.materializeMissingEpisodes`), tagging rows `source='jellyfin'` on `series_episodes`/`series_seasons`. TMDB stays authoritative — its `INSERT OR REPLACE` resets `source` to the `'tmdb'` default and enriches in place, clearing the per-episode "metadata pending" badge (`EpisodeDto.MetadataPending`). Projection-only, no new event (integration-m4k7p, ADR 0012). The materialization also fetches a still image best-effort (`Jellyfin.getPrimaryImageWithReauth` + `JellyfinImport.fetchEpisodeStill`, reusing the ADR-0011 re-auth policy), stored at a **distinct `stills/{slug}-sXXeYY-jellyfin.jpg` path** rather than TMDB's canonical `stills/{slug}-sXXeYY.jpg` — this keeps `SeriesRefresh`'s `ImageStore.imageExists` short-circuit from ever seeing the Jellyfin file at TMDB's path, so a later TMDB refresh still downloads and repoints `still_ref` at its own canonical file. Any still-fetch failure degrades silently to `still_ref = NULL`, never a sync error (integration-007, closes the ADR 0012 deferral). Once TMDB later enriches an episode, the `-jellyfin.jpg` file becomes unreferenced on disk — a deliberately accepted orphan (small, bounded, not proactively cleaned up to avoid coupling `SeriesRefresh` to Jellyfin storage conventions) that Administration's image-cache orphan scan/purge (ADR-0025) can find and reclaim like any other orphan (ADR-0039). A row already present in the projection is also a still **backfill** candidate: `SeriesProjection.getJellyfinEpisodesMissingStill` (`source='jellyfin' AND still_ref IS NULL`) finds rows materialized before the fetch above was wired up (or ones Jellyfin has simply never had an image for), and `SeriesProjection.backfillEpisodeStill` fills the still via a dedicated `UPDATE` — `materializeEpisode`'s `INSERT OR IGNORE` can never touch an existing row, so this is the only write path that can. No refetch guard: a permanently image-less episode is retried on every sync, accepted as bounded and self-draining (integration-q7wv3, ADR-0040).
- **Scheduled job** — recurring task scheduled by `ScheduledJobs.fs` (Steam playtime, Series episode/TMDB refresh per task 042, etc.). Note: Jellyfin auto-sync (task 037) is *not* a scheduled job — it is client-init triggered with a cooldown.
- **Web API key** — the *other* Steam credential, wholly independent of the Family **refresh token**/**access token** pair above: a `key=` query parameter (`steam_api_key`, SettingsStore) authenticating `IPlayerService/GetOwnedGames` and `ISteamUser/GetPlayerSummaries`. Valve can revoke it unilaterally (e.g. as part of flagging an account "possibly compromised"), answering with a plain HTTP 401 — indistinguishable from a rejected family token by symptom alone ("401") but requiring a completely different remedy (regenerate at `steamcommunity.com/dev/apikey`, not reconnect Steam). `Steam.tryGetOwnedGames`/`SteamWebApiError` (integration-r8kwd) type this failure as `KeyRejected` rather than letting `EnsureSuccessStatusCode` throw, so the Family import's own-ownership-enrichment supplement (`Api.fs`'s `runSteamFamilyImport`, a best-effort call — it exists only to backfill `owner_steamids` when Steam's `GetSharedLibraryApps` omits the caller's own id) degrades instead of aborting the whole import, and the two credentials' failures never share wording: family token rejection reads `"family token rejected: ..."` (ADR-0070); Web API key rejection reads `"Steam Web API key rejected (401) — generate a new key at steamcommunity.com/dev/apikey ..."`, persisted to `steam_api_key_last_error` (SettingsStore, cleared on a subsequent successful call or on saving/testing a key) so Settings → Steam can show a standing notice rather than a one-shot toast. **An empty `GetOwnedGames`/`GetRecentlyPlayedGames` response is itself ambiguous and must never be read as success or as evidence the key is bad** (integration-k4vqm): Steam answers `{"response":{}}` for BOTH "this account owns/recently played nothing" and "the target profile's Game Details privacy is not Public" — a fact no caller in this codebase controls or can detect changing. Three call sites used to get this wrong: `testSteamApiKey`'s original probe hardcoded a *third-party* SteamID and reported a good key as "may be invalid" whenever that stranger's privacy setting was non-public; the Family import's owned-games supplement cleared a standing `steam_api_key_last_error` notice on `Ok []` as if it were a real success; the scheduled playtime sync threw an unattributed opaque exception on a rejected key instead of persisting the same notice. The fix in each case: test the key against a profile this project actually controls (the builder's own stored `steam_id`, or, absent that, `Steam.tryValidateApiKeyOnly`'s `GetSchemaForGame` probe, which takes no `steamid` at all); treat `Ok []` as *inconclusive*, never as failure or an all-clear; and only clear `steam_api_key_last_error` on a genuinely populated (non-empty) success.

## Aggregates

No domain aggregates. The closest things to internal state are the **scheduled-job registry** and per-adapter caches; both are infrastructure, not aggregates.

## Key events

Integration **does not own its own event stream**. It emits *commands* into the core BCs (`Add_movie_to_library`, `Refresh_series_from_tmdb`, `Set_play_time`, `Set_hltb_hours`, …). The resulting events live in the core BC's stream.

## Key commands

Adapters call into the core BCs; they don't expose their own command bus to the outside. User-facing commands here are operational: "Sync now", "Refresh from TMDB", "Connect with Steam" (attach a library game to a Steam appId, per task 045). The "Connect Steam" one-time QR login this note used to distinguish from (integration-hebjs, authorizing ongoing Family access-token minting) is deleted (integration-v0xmv, ADR-0070) — "Connect with Steam" is now the only "Connect ... Steam" phrase left in this BC.

## Relationships with other contexts

- **Upstream of (via anticorruption):** Movies, Series, Games. Adapters translate external DTOs into core commands.
- **Operational dependency:** Administration (settings — API keys, sync cadence — live there; see `SettingsStore.fs`).

## Frontend gate

Frontend tasks in this BC (sync UI, "connect with Steam" flows, refresh buttons) **must** `depends_on` the design-system styleguide task. See [[design-system]].

## Open questions

- How to expose adapter failures back to the UI consistently — currently varies per adapter.
- Whether to standardize on a single "refresh queue" pattern across adapters or keep them bespoke.
- **Settled 2026-09-05 (integration-v0xmv, ADR-0070):** after a Valve permanent-ban threat traced to the Steam Connect QR login (the third of three account-hijack alerts), Mediatheca no longer performs a Steam login or mints a Steam token, ever — the QR ceremony, the refresh-token mint-and-retry seam, and every SteamKit2 dependency are deleted outright, and the browser-retrieval fallback ADR-0019/ADR-0067 once held in reserve is closed as *will not build* rather than merely deferred. Steam Family import runs only on a manually pasted, browser-obtained access token (see **Manual token** above); scheduled (cron-cadence) Steam Family sync is answered **no** by the same decision — import stays a manual click, permanently, not just "for now".
