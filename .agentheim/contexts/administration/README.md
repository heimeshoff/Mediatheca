# Administration

## Purpose
**Operational plumbing.** Settings, event store, projection mechanics, event browser, image storage. The infrastructure surface that keeps the single-user app running and inspectable.

## Classification
**generic** — Generic infra for any event-sourced app of this shape.

## Actors
Single user, in an operator role (rebuilding projections, inspecting the event log, configuring API keys).

## Ubiquitous language

- **Event** — an immutable record appended to the event store. Each carries an aggregate id, a type, payload, and a position.
- **Event store** — the SQLite-backed append-only log (`EventStore.fs`). WAL mode, NORMAL sync, FK enabled.
- **Projection** — derived read model rebuilt from the event log (`Projection.fs` plus per-BC `*Projection.fs`).
- **Event browser** — the UI surface for inspecting / searching the event log (task 014). Lives as the Events tab of the Admin console. Search is full-text over event payloads via a SQLite FTS5 index (`events_fts`, external-content over `events.data`); filters (stream, event type, bounded context, timestamp range) compose and are expressed as `EventFilter`; results page via `EventPageQuery`/`EventPage` using keyset (not offset) pagination on `global_position` — see ADR-0020. Stream ids in the explorer's rows are clickable and open the stream drill-in. A **Follow toggle** puts the browser into live-tail mode: polls `IAdminApi.getEventsAfter` every ~2s for events after the last-seen `global_position`, matching the active filters, and prepends them with a brief arrival highlight. Follow is only available on the newest page (`CurrentBefore = None`) and is force-stopped by pagination in either direction, by explicit toggle-off, and by navigating away from the Admin page entirely (root `State.Url_changed` bumps the Follow epoch on `AdminModel` when leaving `Admin _` for any other page, so a poll or in-flight response scheduled before the navigation can't outlive it) — see ADR-0023.
- **Stream drill-in** — `/admin/streams/<streamId>` (`Router.Stream_detail`, `src/Client/Pages/StreamDetail/`): one stream's full event history (via `EventStore.readStream` + `EventFormatting.formatEvent`) juxtaposed with what the matching projection currently says about it, per ADR-0002. Each timeline entry has a raw-JSON toggle (data, metadata, global/stream position); events with no known formatter render as raw JSON marked "unformatted" instead of disappearing. A "current state" panel shows the projection row(s) for Movie/Series/Game/Friend/Catalog streams, dispatched by stream prefix onto each BC's existing `*Projection.getBySlug`, with a link to the media detail page when one exists. Known reference fields in payloads (`friendSlug`, `movieSlug`, `seriesSlug`, `gameSlug`) render as cross-links to the referenced stream's own drill-in page — see ADR-0022 for why a dangling reference is safe to link (it degrades to an empty timeline, not an error).
- **Admin console** — the `/admin` tabbed section (`src/Client/Pages/Admin/`) hosting all operator-facing tooling: Events (event browser), Projections, Health, Images, Jobs, Surgery. Tabs are URL-addressable (`/admin/events`, `/admin/projections`, ...) via `Router.AdminTab`. `/events` is a legacy alias that resolves to the Events tab. `/admin/streams/<streamId>` (the stream drill-in) is a sibling top-level route, not an `AdminTab` variant, since it's parameterized.
- **Images tab** (`/admin/images`, `src/Client/Pages/AdminImages/`) — the `images/` cache's own admin surface (administration-xx3mw): always-available size/count stats with a per-subfolder breakdown (`getImageCacheStats`), **orphan detection** (`listOrphanedImages`), and a hard-delete **cache purge** (`purgeOrphanedImages`, filesystem-only — the event store is never touched). An **orphaned image** is a file under `images/` whose relative path (forward-slash normalized, case-sensitive ordinal) isn't held by any of the fifteen typed ref-bearing projection columns registered in `Administration.imageRefColumns` — the **referenced-ref set** (`Administration.getReferencedImageRefs`, one `Set<string>` built by querying those columns directly, never event replay). The **not-dirty guard** (`Administration.isAnyProjectionDirty`) blocks both the orphan scan and the purge — returning `OrphanScanBlocked`/`PurgeBlocked` with an operator-facing reason, not an exception — while any of the six checkpoint-tracked `projectionHandlers` is mid-rebuild or lagging behind the store head; `cast_members`/`game_journal_blocks` are imperative writes outside that registry and need no gating. Purge re-checks the guard and re-derives the referenced/orphan sets fresh at commit time (TOCTOU-safe), deleting only the intersection of what's requested and what's still genuinely orphan via `ImageStore.deleteImage`; anything that became referenced or already vanished since the scan is skipped and reported, never wrongly deleted. See ADR-0025.
- **`IAdminApi`** — the admin console's own Fable.Remoting contract (`src/Shared/Shared.fs`), separate from `IMediathecaApi` so admin plumbing doesn't bloat the domain API surface (ADR-0004 allows multiple Remoting APIs on one server; see ADR-0017). Routed under `/api/admin/{Method}` via `AdminRoute.builder`. Implemented server-side by `src/Server/Administration.fs` (`Administration.create factory dbPath imagesDir projectionHandlers scheduledJobs recorder` — `dbPath`/`imagesDir` are the same paths `Composition.fs` derives from `DATA_DIR`; `projectionHandlers` is the same registry `Api.create` uses; `scheduledJobs`/`recorder` are the Jobs tab's registry and job-runs recorder, see below; `factory: unit -> SqliteConnection` is the per-request connection factory, ADR-0033 — each record member opens its own `use conn = factory ()`). Event-explorer methods: `getEventPage` (filtered, keyset-paginated), `getEventsAfter` (filtered live-tail poll, ADR-0023), `getEventStreams`, `getEventTypes`, `getBoundedContexts`. Stream drill-in: `getStreamDetail: string -> Async<StreamDetailDto>` (`StreamDetailDto` = `Entries: StreamTimelineEntry list` + `ProjectionRows: ProjectionStateRow list`). Compensating-event composer methods (administration-xjmda, ADR-0032, see below): `getCompensatingEventTypes`, `getCompensatingEventTemplate`, `previewCompensatingEvent`, `appendCompensatingEvent`. Health method: `getHealthStats`. Projections method: `getProjectionStats` (see the Projections tab bullet below). Jobs methods: `getJobStatuses`, `runJobNow` (see the Jobs tab bullet below). Event surgery methods (administration-wwc36, ADR-0034, see below): `previewEventEdit`, `previewEventDelete`, `previewEventTypeRename`, `editEvent`, `deleteEvent`, `renameEventType`, `getBackupStats`.
- **Projections tab** (`/admin/projections`, `src/Client/Pages/AdminProjections/`) — checkpoint/lag/row-count listing for every registered `Projection.ProjectionHandler`, plus an explicit "Rebuild" command per projection (and a "Rebuild all" that drives the same command sequentially across all handlers). The listing comes from `IAdminApi.getProjectionStats : unit -> Async<ProjectionStatRow list>`: for each handler, `Projection.getCheckpointInfo` (checkpoint position + `updated_at`), `Lag` (store head via `EventStore.getMaxGlobalPosition` minus checkpoint), and per-table `RowCount`s from a small hardcoded `projectionName -> table names` map in `Administration.fs` (same "admin-console-only knowledge of a BC's naming convention" pattern as `boundedContextPrefixes`). Rebuild is **not** a Remoting call — it's a raw Giraffe SSE route, `Administration.projectionRebuildStreamHandler`, mounted at `/api/stream/rebuild-projection/{name}` (same streaming pattern as `Api.steamFamilyImportHandler`: `text/event-stream`, `data: {"type":...}\n\n` framed messages). It calls `Projection.rebuildProjectionWithProgress` (drop + replay via the existing `Projection.rebuildProjection` machinery, but reporting a `Projection.RebuildProgress` — `Position`/`Head`/`EventsProcessed` — after every 100-event batch) and streams `progress` events, then a `complete` event. A module-level `ConcurrentDictionary` (`Administration.rebuildingProjections`) guards against two concurrent rebuilds of the same projection: a second request for a projection already rebuilding gets a `rejected` SSE event instead of running. The startup-time forced rebuild of Series/Game that used to live in `Composition.fs` is retired — `buildApp` now only calls `Projection.startAllProjections` (plain incremental catch-up); a full rebuild is this explicit operator command instead. See ADR-0024.
- **Drift check** (administration-btvqa, ADR-0031) — the Projections tab's "Run check" control: for every registered `Projection.ProjectionHandler`, in registration order (load-bearing — see below), a **throwaway `SqliteConnection("Data Source=:memory:")`** is drop+init'd and fully replayed from the live event log via `Projection.replayIntoShadow` (a `conn`-decoupled sibling of `rebuildProjection` — reads via `EventStore.readAllForward liveConn`, writes via `handler.Handle shadowConn`, skips checkpoint writes entirely), then diffed row-by-row against the live tables. Every `*Projection.fs` handler body runs completely unmodified against the shadow connection — no table-name prefixing, no `ATTACH` — so "read-only against live" holds by construction, not convention (ADR-0031; rejected table-prefix/`ATTACH` alternatives would require rewriting 15+ literal-table-name SQL statements per handler). **All handlers finish replaying before any table is diffed** — `FriendProjection`'s `Friend_removed` case scrubs `movie_detail`/`watch_sessions` by literal table name, so diffing `MovieProjection`'s tables before `FriendProjection` has run would report the about-to-be-corrected values as false drift. The diff (`Administration.checkProjectionDrift`/`diffTable`) keys each table's rows on its declared primary key — read generically via `PRAGMA table_info`, not a hand-maintained registry — and reports three discrepancy kinds per `(table, primaryKey)`: `onlyInLive`, `onlyInShadow`, `columnMismatch` (naming the differing columns). Gated by the same not-dirty guard image-cache orphan detection uses (`isAnyProjectionDirty`, ADR-0025) — refused with an operator-facing reason (`driftCheckRejectionMessage`), not an exception, since shadow-at-head vs. live-behind-head would report false drift — and its own single-flight `ConcurrentDictionary` guard (`driftCheckInProgress`, **not** `rebuildingProjections`, whose "live tables are being written" meaning never applies to a read-only check). Transport is a raw Giraffe SSE route, `Administration.driftCheckStreamHandler` at `/api/stream/drift-check`, reusing `Sse.sseFrame` and the same `progress`/`complete`/`rejected` vocabulary `projectionRebuildStreamHandler` established. Results are display-only, never persisted.
- **Event log export/import** (administration-vrc56, ADR-0029) — the event log's portable form, surfaced as a **Backup** section on the Projections tab. **Export** (`GET /api/stream/export-events`, `Administration.exportEventsStreamHandler`) streams the full log as NDJSON — one fixed-field-order JSON object per line (`globalPosition, streamId, streamPosition, eventType, data, metadata, timestamp`), ascending `global_position`, walking `EventStore.readAllForward`'s existing batching so the whole log is never held in memory as one collection/string. `data`/`metadata` are embedded as JSON-escaped **string** values holding the literal `events.data`/`events.metadata` TEXT content — never reparsed and re-nested as JSON objects — a deliberate choice (ADR-0029) that guarantees a lossless, byte-stable round-trip independent of any payload's own JSON-serialization conventions. **Import** (`POST /api/stream/import-events`, `Administration.importEventsStreamHandler`) accepts the request body *as* the NDJSON (no multipart wrapper), reading line-by-line via `EventStore.importNdjson`; it refuses immediately (`ImportFailure.StoreNotEmpty`, surfaced as an SSE `rejected` event) if the target store already has events, before a single line of the body is consumed — import into a non-empty store is a separate operation (administration-n8kqw). A successful import preserves each line's `global_position` **exactly** via an explicit-rowid `INSERT` that bypasses `EventStore.appendToStream` (SQLite's own `AUTOINCREMENT` bookkeeping then continues correctly from `(imported max) + 1`), runs the whole import in one transaction (a malformed line anywhere rolls back everything, leaving the store empty rather than partially populated), and leaves `projection_checkpoints` untouched — the store reads as dirty via the existing ADR-0025-style lag detection until the operator explicitly runs the existing Rebuild-all control (administration-qjcp4, ADR-0024) rather than import self-triggering a second rebuild path. Both `EventStore.exportNdjson (conn) (writer: TextWriter)` / `EventStore.importNdjson (conn) (reader: TextReader)` are Giraffe-decoupled, so the round-trip is a plain Expecto test (`EventStoreNdjsonTests.fs`) with no HTTP pipeline; the Giraffe handlers are thin wrappers that additionally opt into Kestrel's `AllowSynchronousIO` escape hatch (ADR-0029) since the pinned synchronous `TextWriter`/`TextReader` interface otherwise collides with Kestrel's default ban on synchronous request/response-body I/O once a real (non-`StringWriter`/`StringReader`) stream is involved.
- **`EventFilter`** / **`EventPageQuery`** / **`EventPage`** — the composable filter and keyset-pagination query/result shapes for the event explorer (`src/Shared/Shared.fs`; server-side query engine in `EventStore.queryEventPage`, `EventStore.QueryFilter`). See ADR-0020. Reused as-is by the live-tail query.
- **`EventTailQuery`** — "everything after global position `After` matching `Filter`, capped at `Limit`" (`src/Shared/Shared.fs`; server-side `EventStore.queryEventsAfter`, sharing `EventStore.buildFilterConditions` with `queryEventPage`). The ascending counterpart ADR-0020 deliberately left off `EventPageQuery`. See ADR-0023.
- **Health tab** (`/admin/health`, `src/Client/Pages/AdminHealth/`) — store-wide diagnostics: total event count, per-bounded-context breakdown, a 90-day daily-activity sparkline, top-10 largest streams, distinct/top event types, storage sizes (`mediatheca.db`, WAL sidecar, `images/` cache), and the **unknown-event report** (administration-gxd6e, below). Loads from one aggregate DTO, `HealthStats` (`IAdminApi.getHealthStats`), so the whole tab is a single round trip. The per-stream and per-event-type aggregates are index-only `GROUP BY` scans (`EventStore.getEventCountsByStream`/`getEventCountsByType`); the daily counts are bounded to the ~90-day window via an indexed timestamp range (`EventStore.getDailyEventCounts`) rather than scanning the whole table. See ADR-0021 for the full cost reasoning and the growth threshold at which this would need a materialized summary table instead.
- **Unknown-event report** (administration-gxd6e) — surfaces schema drift on the Health tab as two lists over `HealthStats.UnhandledEventTypes`/`UnformattableEventTypes` (each a `UnknownEventTypeRow list`: event type, count, one sample event's raw JSON), built from `EventStore.getEventCountsByType` (already scanned for the Health tab, no new query cost) plus one indexed point lookup per distinct type (`EventStore.getSampleEventForType`). Each BC's `Serialization` module now hand-declares `handledEventTypes: string list` — the same literal strings already appearing as `deserialize` match arms (F# pattern matches aren't reflectively introspectable, so this can't be derived, only kept in lockstep) — registered in `Administration.handledEventTypesByBoundedContext` alongside `boundedContextPrefixes`. Two **independent** checks per event type, run against one sample stored event: **unhandled** — the type's owning BC (resolved via stream prefix) doesn't list it in its `handledEventTypes`, or the prefix matches no known BC at all; **unformattable** — that sample event, run through `EventFormatting.formatEvent`, returns `None`. A type can land in neither, either, or both lists — e.g. before administration-qk3f7 closed it, `Game_rawg_id_set` was handled by `Games.Serialization.deserialize` but had no case in `EventFormatting.formatGameEvent` (unformattable but not unhandled), the one real handled-but-unformattable drift the report ever caught; `EventFormatting.formatGameEvent` now has a `Game_rawg_id_set` case, so `handled ⟺ formattable` holds for every real event type currently in the store. Display-only, not persisted.
- **Jobs tab** (`/admin/jobs`, `src/Client/Pages/AdminJobs/`) — durable history and manual triggering for the two `ScheduledJobs.JobSpec` entries (Steam playtime sync, Series TMDB refresh), per **ADR-0026**. Every fire — the daily timer or an operator's "Run now" — is recorded as a **job run**: a `job_runs` row (`job_name`, `trigger` = `scheduled`|`manual`, `status` = `running`|`ok`|`error`|`skipped`|`interrupted`, `summary`, `started_at`/`finished_at` — timestamps stored ISO-8601 UTC). The shared choke point is `ScheduledJobs.tryStartJob recorder spec trigger`, which claims a name-keyed in-memory guard (`Administration.runningJobs`, an exact structural copy of `rebuildingProjections`) and wraps the job body in a try/finally that **guarantees** the row reaches a terminal status — `ok`/`skipped` from a clean `JobRunOutcome`, `error` (with the exception message) from an uncaught exception — and always releases the guard slot; a second trigger of the same job name, from either source, is refused with no row written. **Run-now is fire-and-forget**: `IAdminApi.runJobNow` returns `RunJobStarted runId` (or `RunJobRejected`) *before* the job completes — a plain Remoting call, not SSE, since the tab just polls `getJobStatuses` (reusing ADR-0023's epoch-guarded polling `Cmd`) until the row resolves. **Crash reconciliation happens only at server startup** (`Administration.initializeJobRuns`, called before `ScheduledJobs.startAll`): any row still `running` at boot is definitionally orphaned (the in-memory guard is empty on a fresh process) and is marked `interrupted`; this never runs on a read path, since reading can't distinguish a live in-flight run from a crash. The **injected recorder seam** (`ScheduledJobs.JobRunRecorder`, implemented by `Administration.makeJobRunRecorder conn`) exists because `ScheduledJobs.fs` compiles before `Administration.fs` and must not depend on it — `Composition.fs` builds one recorder instance and passes it to both `ScheduledJobs.startAll` and `Administration.create`, so the scheduled timer and manual run-now share one guard and one connection. `SeriesRefresh.runNightlyJob` and `PlaytimeTracker.runSync` (Integration BC) return their natural result types; the `JobRunOutcome` mapping happens in `Composition.fs`'s job-body closures, not in the Integration modules themselves.
- **Setting** — a configuration value persisted in `SettingsStore.fs`. API keys, sync cadence, Jellyfin URL, Steam credentials, etc.
- **Image ref** — a stable identifier for a stored image (posters, backdrops, friend avatars). The image store (`ImageStore.fs`) is the source of truth; aggregates reference images by ref.
- **Slug** — domain-stable identifier used across BCs (friend slug, movie slug, etc.). Generated by `Slug` module in Shared.
- **Playwright e2e harness** (`playwright.config.ts`, `tests/e2e/`, ADR-0027) — the project's first browser/e2e test harness, first exercised on the Events tab's Follow toggle. `webServer` drives the real dev stack via non-watch `dotnet run` (not `dotnet watch` — its child process tree orphans on Windows teardown), each run gets a fresh temp `DATA_DIR` (never the real dev DB), and "event appended elsewhere" is triggered via a direct Fable.Remoting HTTP call (`POST /api/{TypeName}/{Method}`, body = a JSON array of arguments even for one arg), not a raw event-store write or UI clicking. `getEventsAfter` traffic is observable via the vite-proxied `:5173` origin, not just `:5000`. Run via `npm run test:e2e`. Standing up the harness surfaced **administration-tj8n2**: the two `ScheduledJobs` catch-up timers raced on the shared `SqliteConnection` and could crash a freshly cold-started server — fixed for real by ADR-0028 (dedicated job connection + per-command lock), so the interim `MEDIATHECA_DISABLE_SCHEDULED_JOBS=1` e2e-only workaround is retired and jobs run unconditionally, same as every other environment. `event-tail-follow.spec.ts` (administration-a4d9b) codifies ADR-0023's three Follow-toggle behaviors as committed specs on top of this harness — arrival + `animate-highlight`, filter-respecting live rows, and all three no-orphan-polling sub-cases (toggle-off, pagination-away, and the load-bearing real client-side navigate-away that was previously only guarded by static review). Its specs originally triggered events sequentially, never concurrently, via `addFriend` — concurrent calls empirically crashed the shared connection (`SqliteConnection does not support nested transactions`), which motivated **administration-cx92m**'s request-concurrency audit (ADR-0030's interim gate) and **administration-mz6kp**'s per-request connection factory (ADR-0033) that superseded it; `addFriends` fires concurrently (`Promise.all`) and a dedicated repeated-burst test is the regression proof. It also surfaced **administration-nf3wk**: the event explorer's zero-filter-match state used to render `"No events found."`, the same message as a genuinely empty store, with `paginationBar`'s own `"No matches"` string left unreachable dead code given the `view` branch order. Resolved by `EventBrowser.State.emptyStateMessage`/`anyFilterActive` (`Model`'s six string filter fields), which now render `"No matches for the current filters."` distinctly whenever a filter is active; `paginationBar`'s dead branch was removed (it only ever renders once `model.Events` is non-empty, so `TotalMatches > 0` there).
- **Compensating-event composer** (administration-xjmda, **ADR-0032**) — the stream drill-in's "Append corrective event" action: the idiomatic event-sourcing fix for bad data is appending a corrective event, not mutating history (ADR-0002), and this is the safe path before any raw-surgery tooling exists (it `blocks` administration-wwc36, the escape hatch for when this pattern doesn't apply). The operator picks an event type from those seen anywhere under the stream's bounded-context prefix (`IAdminApi.getCompensatingEventTypes`, `EventStore.getDistinctEventTypesForPrefix`), pre-fills the payload by cloning the most recent real instance of that type — the target stream itself first, falling back BC-prefix-wide (`getCompensatingEventTemplate`, `EventStore.getMostRecentEventOfType`) — edits it, then previews and commits. **Validate-by-round-trip**: `Administration.eventCodecs` wraps each BC's own public `Serialization.serialize`/`deserialize` seam (no DU reflection, no template registry — see ADR-0032 for why both were rejected) as `deserialize eventType data |> Option.map serialize`, dispatched by stream-id prefix the same `if/elif StartsWith` way `EventFormatting.formatEvent` dispatches formatters. The bytes actually appended are the *re-serialized canonical form*, never the operator's raw edit; a payload that fails to deserialize is refused outright (no row inserted). `previewCompensatingEvent` reads the current `expectedPosition` and returns the canonical preview for the confirmation dialog; `appendCompensatingEvent` takes that same `expectedPosition` back as a caller-supplied value and re-validates independently before appending via `EventStore.appendToStream` (pure INSERT, expected-position concurrency-checked — never the explicit-rowid path `importNdjson` uses), then runs catch-up over every registered `projectionHandlers` entry, identical to `Api.executeCommandCore`'s idiom. Appended rows carry `metadata = {"source":"admin-console"}` — the one intentional, projection-invisible difference from an organic event. Like every other request-reachable transaction site, this runs on the connection `appendCompensatingEvent` opened for this one request (`use conn = factory ()`, ADR-0033) — no lock needed, since no other request shares that connection object. The confirmation dialog is a paper-overlay modal (ADR-0016, via `Components.ModalPanel`) showing the exact canonicalized payload about to be appended.
- **Event surgery** (administration-wwc36, **ADR-0034**) — the Surgery tab (`/admin/surgery`, `src/Client/Pages/AdminSurgery/`): the raw-log escape hatch for cases the compensating-event composer (administration-xjmda, ADR-0032, which `blocks`-depended this task so the safe path always ships first) can't reach — a genuinely wrong-payload event, or a stranded event-type name left by a code-side DU rename. Three operations, **edit** (`UPDATE events SET data, metadata`), **delete** (`DELETE FROM events`), and **rename** (`UPDATE events SET event_type` store-wide), each behind the identical three-guardrail protocol: (1) **`VACUUM INTO` backup first**, on the op's own per-request connection (`use conn = factory ()`, ADR-0033), run in autocommit *before* any `BeginTransaction` (SQLite refuses `VACUUM` inside a transaction) — verified by opening the backup on a throwaway, unconfigured connection (never `configureConnection`, which would flip a plain file to WAL) and checking `PRAGMA integrity_check` + a row count; `VACUUM INTO`/verify failure aborts with **no row touched**, surfaced as the typed `SurgeryResult.BackupFailed reason` rather than an exception (mirrors `OrphanScan`/`PurgeResult`'s idiom); success carries `SurgeryResult.Applied(backupPath, affectedRows)`. (2) **Preview + explicit confirm** — `previewEventEdit`/`previewEventDelete` return the one targeted row by `global_position` (`SurgeryEventRow`, edit/delete's target; delete's preview additionally carries `StreamCurrentPosition` so the client can render the gap-consequence copy), `previewEventTypeRename` returns an exact `Count` plus a bounded `Sample`; every preview is a pure read, so cancelling (never committing) leaves `events`/`events_fts`/`projection_checkpoints` untouched by construction — confirmation is a paper-overlay modal (ADR-0016, `Components.ModalPanel`, same as the composer's). (3) **Projections-dirty signal** — the mutation, an `events_fts` `('rebuild')` resync (edit/delete only; rename doesn't touch `data` so needs none — reusing the exact idiom `EventStore.createFtsIndex`'s own backfill uses, since `events_fts` has only an `AFTER INSERT` trigger and never before had an UPDATE/DELETE path to cover), and a rewind of every checkpoint-tracked projection's checkpoint to 0 (`Projection.saveCheckpoint handler.Name 0L`) all share **one transaction** on the same connection (mutate-then-rebuild order, load-bearing for delete: the FTS rebuild must see the row already gone). `Administration.isAnyProjectionDirty` (ADR-0025, unmodified) then reports every handler dirty until the operator reruns Rebuild-all (administration-qjcp4, ADR-0024) — the same "leave dirty, reuse Rebuild-all" precedent ADR-0029 set for NDJSON import. **Delete leaves permanent `stream_position`/`global_position` gaps by design** (no renumbering) — verified safe against `appendToStream`'s fresh `MAX` re-read, `getMaxGlobalPosition`'s deliberate `MAX` (not `COUNT`), and the keyset/live-tail cursors' strict `</>` semantics. A cross-tab **"projections out of sync — rebuild" banner** in the Admin shell (above the tab bar, every tab) is client-derived from `getProjectionStats`'s `Lag` field — no new API method; `Admin.State`'s `Surgery_msg` handler reloads `ProjectionsModel.Stats` immediately after every committed mutation so the banner reacts without waiting for a tab revisit. **Backup retention is keep-all** — `backups/` (a sibling directory of the live db file, derived from `dbPath`) is never pruned by this feature; `getBackupStats` is a plain directory walk (`Count`, `TotalBytes`) feeding the Surgery tab's stats panel.
- **Per-request connection factory** (administration-mz6kp, **ADR-0033**, supersedes administration-cx92m's ADR-0030) — every request/SSE operation opens and disposes its own `SqliteConnection`, retiring the single shared request-serving `conn` ADR-0030's interim `requestDbLock` gate used to guard. `Composition.buildApp` builds `connectionFactory : unit -> SqliteConnection` (`Composition.createConnectionFactory`) — pragmas re-applied on every open via `EventStore.configureConnection`, table/FTS creation staying a one-time step on the separate bootstrap `conn`. `Api.create`/`Administration.create` take this factory instead of a live connection; every record member opens exactly one `use conn = factory ()` inside its own `async`/`task` scope (never a bare `let`, never a `use` outside the async scope — either leaks the connection past the request), and multi-append members (`removeMovie`, the Steam/Jellyfin import loops) hold that one connection across every append they make. The five raw Giraffe SSE handlers (`Api.steamFamilyImportHandler`, `Administration.exportEventsStreamHandler`/`importEventsStreamHandler`/`projectionRebuildStreamHandler`/`driftCheckStreamHandler`) each open one connection for the whole stream, not per DB call. `JellyfinSync.triggerSync`'s background sync (genuinely detached via `Async.Start`, so it can't borrow a request-scoped connection) opens its own connection *inside* the spawned background async instead. This closes the residual read×write/read×read race ADR-0030 explicitly left open, by removing the shared mutable connection object entirely rather than locking around it — safe per ADR-0028's finding that WAL + `busy_timeout` serialize writes at the *file* level across separate connections (proven first for the dedicated job connection, generalized here to one connection per request). ADR-0028's `jobConn`/`jobDbLock` and the vestigial `manualSyncTriggerLock` are unaffected — they guard a different connection object for a different reason. `tests/Server.Tests/TestDb.fs` (`TestDb.withTempDbFactory`) is the shared per-test, file-backed fixture the affected test files now build on (not shared-cache `:memory:`, which doesn't exercise WAL's file-level serialization and is destroyed when its last connection closes).

## Aggregates

No domain aggregates. The store and registry tables are infrastructure.

## Key events

The event store **carries** events from every BC but does not own a stream of its own. There is no `Administration_*` event family.

## Key commands

Operational: "rebuild projection X", "set setting Y", "save image Z". These are command-shaped but not in the same sense as core BC commands.

## Relationships with other contexts

- **Shared kernel** with every BC: the event store and image store are consumed everywhere.
- **Supports:** Integration (settings live here, adapters read them).

## Frontend gate
