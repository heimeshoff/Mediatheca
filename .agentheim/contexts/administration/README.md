# Administration

## Purpose
**Operational plumbing.** Settings, event store, projection mechanics, event browser, image storage. The infrastructure surface that keeps the single-user app running and inspectable.

## Classification
**generic** — Generic infra for any event-sourced app of this shape.

## Actors
Single user, in an operator role (rebuilding projections, inspecting the event log, configuring API keys).

## Ubiquitous language

- **Event** — an immutable record appended to the event store. Each carries an aggregate id, a type, payload, and a position.
- **Event store** — the SQLite-backed append-only log (`EventStore.fs`). WAL mode, NORMAL sync, FK enabled.
- **Projection** — derived read model rebuilt from the event log (`Projection.fs` plus per-BC `*Projection.fs`).
- **Event browser** — the UI surface for inspecting / searching the event log (task 014). Lives as the Events section of Settings' inline administration panel (administration-k3vmt; formerly the Events tab of a standalone `/admin` console — see the Admin console bullet below). Search is full-text over event payloads via a SQLite FTS5 index (`events_fts`, external-content over `events.data`); filters (stream, event type, bounded context, timestamp range) compose and are expressed as `EventFilter`; results page via `EventPageQuery`/`EventPage` using keyset (not offset) pagination on `global_position` — see ADR-0020. Stream ids in the explorer's rows are clickable and open the stream drill-in. A **Follow toggle** puts the browser into live-tail mode: polls `IAdminApi.getEventsAfter` every ~2s for events after the last-seen `global_position`, matching the active filters, and prepends them with a brief arrival highlight. Follow is only available on the newest page (`CurrentBefore = None`) and is force-stopped by pagination in either direction, by explicit toggle-off, by collapsing the Events section without navigating, and by navigating away from the Settings page entirely (root `State.Url_changed` bumps the Follow epoch on the Events section's model when leaving `Settings` for any other page, so a poll or in-flight response scheduled before the navigation can't outlive it) — see ADR-0023, amended by ADR-0041.
- **Stream drill-in** — `/admin/streams/<streamId>` (`Router.Stream_detail`, `src/Client/Pages/StreamDetail/`): one stream's full event history (via `EventStore.readStream` + `EventFormatting.formatEvent`) juxtaposed with what the matching projection currently says about it, per ADR-0002. Each timeline entry has a raw-JSON toggle (data, metadata, global/stream position); events with no known formatter render as raw JSON marked "unformatted" instead of disappearing. A "current state" panel shows the projection row(s) for Movie/Series/Game/Friend/Catalog streams, dispatched by stream prefix onto each BC's existing `*Projection.getBySlug`, with a link to the media detail page when one exists. Known reference fields in payloads (`friendSlug`, `movieSlug`, `seriesSlug`, `gameSlug`) render as cross-links to the referenced stream's own drill-in page — see ADR-0022 for why a dangling reference is safe to link (it degrades to an empty timeline, not an error). Its "← Back to Event Store" link points at Settings (ADR-0041) — it was already a top-level `Page` case rather than an `AdminTab` variant (administration-v4y9g), so it outlived the `/admin` console's dissolution unchanged apart from that link.
- **Administration section of Settings** (formerly a standalone `/admin` tabbed console, dissolved by administration-k3vmt/**ADR-0041**) — six inline collapsible sections below Settings' Data Imports section, in a fixed order: Events (event browser), Projections, Health, Images, Jobs, Surgery. `Pages/Admin/` survives as a headless composite child (`Settings.Types.Model.AdminModel`, one `Admin_msg` wrapper) holding the same six child models the old tabbed shell did; `Pages/Admin/Views.fs` exposes one render function per section instead of a tab-switched `view`. `/settings` is the only address — every former admin URL (`/admin`, all six `/admin/<tab>` segments, the legacy `/events` alias) resolves to `Settings` with no section-level route; `/admin/streams/<streamId>` (the stream drill-in, see above) is the one exception, since it's parameterized rather than a fixed section. **Lazy load, one exception**: a collapsed section issues no query; each section fires its own load message once, on first expand, never again on re-expand. The exception is Projections' `getProjectionStats`, which fires on every `/settings` visit regardless of collapse state (wired into root `State.Url_changed`, not `Settings.State.init`), since the ADR-0034 dirty banner is client-derived from it. `BottomNav.dockItems` (already Settings-only) reaches the whole console on mobile for the first time.
- **Images tab** (the Images section of Settings' inline administration panel, `src/Client/Pages/AdminImages/`) — the `images/` cache's own admin surface (administration-xx3mw): always-available size/count stats with a per-subfolder breakdown (`getImageCacheStats`), **orphan detection** (`listOrphanedImages`), and a hard-delete **cache purge** (`purgeOrphanedImages`, filesystem-only — the event store is never touched). An **orphaned image** is a file under `images/` whose relative path (forward-slash normalized, case-sensitive ordinal) isn't held by any of the fifteen typed ref-bearing projection columns registered in `Administration.imageRefColumns` — the **referenced-ref set** (`Administration.getReferencedImageRefs`, one `Set<string>` built by querying those columns directly, never event replay). The **not-dirty guard** (`Administration.isAnyProjectionDirty`) blocks both the orphan scan and the purge — returning `OrphanScanBlocked`/`PurgeBlocked` with an operator-facing reason, not an exception — while any of the six checkpoint-tracked `projectionHandlers` is mid-rebuild or lagging behind the store head; `cast_members`/`game_journal_blocks` are imperative writes outside that registry and need no gating. Purge re-checks the guard and re-derives the referenced/orphan sets fresh at commit time (TOCTOU-safe), deleting only the intersection of what's requested and what's still genuinely orphan via `ImageStore.deleteImage`; anything that became referenced or already vanished since the scan is skipped and reported, never wrongly deleted. See ADR-0025.
- **`IAdminApi`** — the admin console's own Fable.Remoting contract (`src/Shared/Shared.fs`), separate from `IMediathecaApi` so admin plumbing doesn't bloat the domain API surface (ADR-0004 allows multiple Remoting APIs on one server; see ADR-0017). Routed under `/api/admin/{Method}` via `AdminRoute.builder`. Implemented server-side by `src/Server/Administration.fs` (`Administration.create factory dbPath imagesDir projectionHandlers scheduledJobs recorder guards` — `dbPath`/`imagesDir` are the same paths `Composition.fs` derives from `DATA_DIR`; `projectionHandlers` is the same registry `Api.create` uses; `scheduledJobs`/`recorder` are the Jobs tab's registry and job-runs recorder, see below; `factory: unit -> SqliteConnection` is the per-request connection factory, ADR-0033 — each record member opens its own `use conn = factory ()`; `guards: AdminGuards` is the composition root's single per-instance projection-guard value, ADR-0035, see below). Event-explorer methods: `getEventPage` (filtered, keyset-paginated), `getEventsAfter` (filtered live-tail poll, ADR-0023), `getEventStreams`, `getEventTypes`, `getBoundedContexts`. Stream drill-in: `getStreamDetail: string -> Async<StreamDetailDto>` (`StreamDetailDto` = `Entries: StreamTimelineEntry list` + `ProjectionRows: ProjectionStateRow list`). Compensating-event composer methods (administration-xjmda, ADR-0032, see below): `getCompensatingEventTypes`, `getCompensatingEventTemplate`, `previewCompensatingEvent`, `appendCompensatingEvent`. Health method: `getHealthStats`. Projections method: `getProjectionStats` (see the Projections tab bullet below). Jobs methods: `getJobStatuses`, `runJobNow` (see the Jobs tab bullet below). Event surgery methods (administration-wwc36, ADR-0034, see below): `previewEventEdit`, `previewEventDelete`, `previewEventTypeRename`, `editEvent`, `deleteEvent`, `renameEventType`, `getBackupStats`. Wipe-first import method (administration-n8kqw, ADR-0038, see below): `getWipeImportPreview`.
- **Projections tab** (the Projections section of Settings' inline administration panel, `src/Client/Pages/AdminProjections/`) — checkpoint/lag/row-count listing for every registered `Projection.ProjectionHandler`, plus an explicit "Rebuild" command per projection (and a "Rebuild all" that drives the same command sequentially across all handlers). The listing comes from `IAdminApi.getProjectionStats : unit -> Async<ProjectionStatRow list>`: for each handler, `Projection.getCheckpointInfo` (checkpoint position + `updated_at`), `Lag` (store head via `EventStore.getMaxGlobalPosition` minus checkpoint), and per-table `RowCount`s from `projectionTables`, a `projectionName -> table names` map **derived** from `Administration.tableRegistry` (see the table classification bullet below) rather than hand-maintained in parallel. Rebuild is **not** a Remoting call — it's a raw Giraffe SSE route, `Administration.projectionRebuildStreamHandler`, mounted at `/api/stream/rebuild-projection/{name}` (same streaming pattern as `Api.steamFamilyImportHandler`: `text/event-stream`, `data: {"type":...}\n\n` framed messages). It calls `Projection.rebuildProjectionWithProgress` (drop + replay via the existing `Projection.rebuildProjection` machinery, but reporting a `Projection.RebuildProgress` — `Position`/`Head`/`EventsProcessed` — after every 100-event batch) and streams `progress` events, then a `complete` event. An `AdminGuards.RebuildingProjections` `ConcurrentDictionary`, per-instance and composition-root-owned (ADR-0035, see below), guards against two concurrent rebuilds of the same projection: a second request for a projection already rebuilding gets a `rejected` SSE event instead of running. The startup-time forced rebuild of Series/Game that used to live in `Composition.fs` is retired — `buildApp` now only calls `Projection.startAllProjections` (plain incremental catch-up); a full rebuild is this explicit operator command instead. See ADR-0024.
- **Lossy-rebuild guard** (administration-kv7dp, **ADR-0049**) — rebuild is refused outright, server-side, for any projection registered in `Administration.lossyRebuildProjections` (one entry today: `SeriesProjection` — registered when its out-of-band writers, `SeriesRefresh.applyToProjection`'s TMDB refresh and ADR-0012's Jellyfin materialization, still wrote `series_detail`/`series_seasons`/`series_episodes` directly, so `Drop; Init; replay` would have permanently destroyed that state; series-m7fdk/r2xhv have since moved those writes to the cache tier, and `series-d5tpn` proves drift zero and retires this entry). `Administration.lossyRebuildRejectionMessage : string -> string option` is the pure lookup (bypassable via the undocumented `MEDIATHECA_ALLOW_LOSSY_REBUILD=1` env var, server-side only, no UI). `Administration.decideAndClaimRebuildGuard` orders this check FIRST in `projectionRebuildStreamHandler` — before the wipe-import and single-flight checks — since it claims neither guard dictionary; a rejected request reaches the client via the same non-fatal `rejected` SSE event the other two rejection arms already use, so this shipped with **zero client changes**. The same guard gates `CinemarcoImport.runImport`'s post-import rebuild loop, falling back to `Projection.runProjection` (incremental catch-up) for a guarded handler. Deliberately does **not** reuse ADR-0034's `VACUUM INTO`/confirm-modal protocol — that protects the event store, not projection tables, and a confirm modal would be permanent frontend UI (inheriting the design-system gate) built to serve a condition this ADR commits to deleting: its Decision section names the exact retirement criterion (`checkProjectionDrift` reports 0 discrepancies AND no out-of-band writer remains), which `series-d5tpn` executes.
- **Drift check** (administration-btvqa, ADR-0031) — the Projections tab's "Run check" control: for every registered `Projection.ProjectionHandler`, in registration order (load-bearing — see below), a **throwaway `SqliteConnection("Data Source=:memory:")`** is drop+init'd and fully replayed from the live event log via `Projection.replayIntoShadow` (a `conn`-decoupled sibling of `rebuildProjection` — reads via `EventStore.readAllForward liveConn`, writes via `handler.Handle shadowConn`, skips checkpoint writes entirely), then diffed row-by-row against the live tables. Every `*Projection.fs` handler body runs completely unmodified against the shadow connection — no table-name prefixing, no `ATTACH` — so "read-only against live" holds by construction, not convention (ADR-0031; rejected table-prefix/`ATTACH` alternatives would require rewriting 15+ literal-table-name SQL statements per handler). **All handlers finish replaying before any table is diffed** — `FriendProjection`'s `Friend_removed` case scrubs `movie_detail`/`watch_sessions` by literal table name, so diffing `MovieProjection`'s tables before `FriendProjection` has run would report the about-to-be-corrected values as false drift. The diff (`Administration.checkProjectionDrift`/`diffTable`) keys each table's rows on its declared primary key — read generically via `PRAGMA table_info`, not a hand-maintained registry — and reports three discrepancy kinds per `(table, primaryKey)`: `onlyInLive`, `onlyInShadow`, `columnMismatch` (naming the differing columns). Gated by the same not-dirty guard image-cache orphan detection uses (`isAnyProjectionDirty`, ADR-0025) — refused with an operator-facing reason (`driftCheckRejectionMessage`), not an exception, since shadow-at-head vs. live-behind-head would report false drift — and its own single-flight `ConcurrentDictionary` guard (`AdminGuards.DriftCheckInProgress`, **not** `RebuildingProjections`, whose "live tables are being written" meaning never applies to a read-only check). Transport is a raw Giraffe SSE route, `Administration.driftCheckStreamHandler` at `/api/stream/drift-check`, reusing `Sse.sseFrame` and the same `progress`/`complete`/`rejected` vocabulary `projectionRebuildStreamHandler` established. Results are display-only, never persisted.
- **Event log export/import** (administration-vrc56, ADR-0029) — the event log's portable form, surfaced as a **Backup** section on the Projections tab. **Export** (`GET /api/stream/export-events`, `Administration.exportEventsStreamHandler`) streams the full log as NDJSON — one fixed-field-order JSON object per line (`globalPosition, streamId, streamPosition, eventType, data, metadata, timestamp`), ascending `global_position`, walking `EventStore.readAllForward`'s existing batching so the whole log is never held in memory as one collection/string. `data`/`metadata` are embedded as JSON-escaped **string** values holding the literal `events.data`/`events.metadata` TEXT content — never reparsed and re-nested as JSON objects — a deliberate choice (ADR-0029) that guarantees a lossless, byte-stable round-trip independent of any payload's own JSON-serialization conventions. **Import** (`POST /api/stream/import-events`, `Administration.importEventsStreamHandler`) accepts the request body *as* the NDJSON (no multipart wrapper), reading line-by-line via `EventStore.importNdjson`; it refuses immediately (`ImportFailure.StoreNotEmpty`, surfaced as an SSE `rejected` event) if the target store already has events, before a single line of the body is consumed — import into a non-empty store is the separate **wipe-first import** operation below. A successful import preserves each line's `global_position` **exactly** via an explicit-rowid `INSERT` that bypasses `EventStore.appendToStream` (SQLite's own `AUTOINCREMENT` bookkeeping then continues correctly from `(imported max) + 1` — true only on this empty-store path; see wipe-first import below for why it's a strictly-greater guarantee, not a `+1` one, there), runs the whole import in one transaction (a malformed line anywhere rolls back everything, leaving the store empty rather than partially populated), and leaves `projection_checkpoints` untouched — the store reads as dirty via the existing ADR-0025-style lag detection until the operator explicitly runs the existing Rebuild-all control (administration-qjcp4, ADR-0024) rather than import self-triggering a second rebuild path. Both `EventStore.exportNdjson (conn) (writer: TextWriter)` / `EventStore.importNdjson (conn) (reader: TextReader)` are Giraffe-decoupled, so the round-trip is a plain Expecto test (`EventStoreNdjsonTests.fs`) with no HTTP pipeline; the Giraffe handlers are thin wrappers that additionally opt into Kestrel's `AllowSynchronousIO` escape hatch (ADR-0029) since the pinned synchronous `TextWriter`/`TextReader` interface otherwise collides with Kestrel's default ban on synchronous request/response-body I/O once a real (non-`StringWriter`/`StringReader`) stream is involved. `EventStore.importNdjson`'s read-line/decode/explicit-rowid-insert loop is extracted into public `EventStore.importNdjsonRows (conn) (reader)` (administration-n8kqw) — no transaction of its own, caller-owned commit/rollback — purely so the wipe-first path below can share it inside a different transaction; `importNdjson`'s own signature/semantics/`StoreNotEmpty` behaviour are unchanged.

- **Wipe-first event log import** (administration-n8kqw, **ADR-0038**) — overwriting a *non-empty* store, a separate raw Giraffe SSE route (`POST /api/stream/wipe-import-events`, `Administration.wipeImportEventsStreamHandler`), sibling to (not a flag on) `/api/stream/import-events`, so that route's "refuses any non-empty store" invariant stays literally true and never acquires the `dbPath`/`projectionHandlers` dependencies needed to destroy a store. Reuses event surgery's three-guardrail protocol (administration-wwc36, ADR-0034) with one deliberate inversion: `EventStore.vacuumIntoBackup` still takes a backup first, in autocommit, streamed to the client as a `backup` SSE event before anything is touched — but the **transaction**, not the backup file, is the primary restore path, since `Administration.runWipeAndImport` runs `EventStore.deleteAllEvents` (`DELETE FROM events`, schema/FTS/trigger preserved) → `EventStore.importNdjsonRows` → `EventStore.rebuildFtsIndex` → `Projection.saveCheckpoint ... 0L` for every registered handler all in **one transaction**, so a malformed line anywhere rolls back the wipe too. `deleteAllEvents` deliberately does not reset `sqlite_sequence` — a subsequent append lands strictly above the discarded log's own max, not necessarily `(imported max) + 1`, harmless by the same gap-tolerance reasoning ADR-0034 established for delete. `IAdminApi.getWipeImportPreview : unit -> Async<WipeImportPreview>` (backed by a new `EventStore.getEventStoreSummary` — one `COUNT`/`COUNT DISTINCT`/`MIN`/`MAX` query, deliberately not `getHealthStats` or `getDistinctStreams`, both the wrong shape/cost) feeds the client confirm dialog's discard-side stats; the incoming file's line count is computed client-side, no staging area. **Concurrency**: `AdminGuards` (ADR-0035) gains `WipeImportInProgress`, mutually exclusive with `RebuildingProjections` in both directions — a **coherence** guard (the first documented bound on ADR-0033's "WAL + busy_timeout is sufficient" reasoning), since a rebuild replaying against the pre-wipe log could otherwise checkpoint into a discarded log and read as falsely clean. Both directions are extracted as plain, directly-testable functions — `Administration.decideAndClaimWipeImportGuard` (checks `RebuildingProjections` first, refusing with no claim ever made, before `TryAdd`-ing `WipeImportInProgress`; never claims-then-releases) and `Administration.wipeImportInFlight` (the `projectionRebuildStreamHandler`-side check) — rather than left inline and untested, the way `driftCheckStreamHandler`'s/`projectionRebuildStreamHandler`'s own pre-existing single-flight checks are. Client: a second file-input control on the Projections tab's existing Backup section (not the Surgery tab) opens a paper-overlay confirm modal (ADR-0016) showing both the discard-side server stats and the incoming-side client line count together (explicitly calling out a 0-line incoming file as "wipes to empty" rather than blocking it); Cancel is model-only (no request ever sent); Confirm streams `backup` then the terminal outcome and, on success, reloads `ProjectionsModel.Stats` (flips the existing cross-tab dirty banner, ADR-0034) with no auto-navigation, consistent with ordinary import and every surgery mutation.
- **Offline demoted-event filter** (administration-z6ymt, **ADR-0056**, **ADR-0058**) — `EventLogFilter.fs`'s `filterNdjson : Set<string> -> TextReader -> TextWriter -> FilterSummary` is a pure, `SqliteConnection`-free line-level filter over ADR-0029 NDJSON: it parses only each line's `eventType` field and passes every kept line through byte-identical (never reparsed/re-nested), dropping any line whose type is in the caller-supplied deny-list; an unparseable line is kept fail-safe and reported separately in `FilterSummary.UnparseableLines`, never silently dropped. `EventLogFilter.purgeEligibleEventTypes` is the current deny-list (the eleven demoted Game metadata event types `games-v4nqe` made permanently inert). Invoked via a CLI subcommand — `dotnet run --project src/Server -- filter-demoted-events <in> <out>` — dispatched from `Program.fs`'s `main` before `Composition.buildApp` runs, so it never opens `DATA_DIR` or a live connection at all (ADR-0058's rationale for this shape over a standalone `.fsx` script or a new console project). Per ADR-0056, this is worker-built offline tooling only — the operator runs it by hand against an exported file as one step of a larger export → filter → wipe-import → Rebuild-all → drift-check sequence; see `docs/runbooks/purge-demoted-metadata-events.md`. `administration-z6ymt` also retired the completed games-h4mrd play-session-history migration machinery in the same change (`PlaySessionMigration.fs`, both `/api/stream/migrate-play-sessions*` routes, `AdminGuards.PlaySessionMigrationInProgress` and its mutual-exclusion arms in `decideAndClaimWipeImportGuard`/`decideAndClaimRebuildGuard`), following the `StartupCutover.fs` retirement precedent (ADR-0052) now that the migration ran to completion in production (2026-08-02). `StartupCutover.fs`'s own `playSessionPhase` had a hard compile-time dependency on the deleted `Administration.previewPlaySessionMigration`/`runPlaySessionMigration` this task's scope note hadn't anticipated — ADR-0058 records why it was reduced to a guard (verifies `Game_play_time_set` can no longer occur, rather than driving a migration that no longer exists) instead of deleted outright, since `StartupCutover.fs`'s own retirement stayed out of this task's scope.
- **`EventFilter`** / **`EventPageQuery`** / **`EventPage`** — the composable filter and keyset-pagination query/result shapes for the event explorer (`src/Shared/Shared.fs`; server-side query engine in `EventStore.queryEventPage`, `EventStore.QueryFilter`). See ADR-0020. Reused as-is by the live-tail query.
- **`EventTailQuery`** — "everything after global position `After` matching `Filter`, capped at `Limit`" (`src/Shared/Shared.fs`; server-side `EventStore.queryEventsAfter`, sharing `EventStore.buildFilterConditions` with `queryEventPage`). The ascending counterpart ADR-0020 deliberately left off `EventPageQuery`. See ADR-0023.
- **Health tab** (the Health section of Settings' inline administration panel, `src/Client/Pages/AdminHealth/`) — store-wide diagnostics: total event count, per-bounded-context breakdown, a 90-day daily-activity sparkline, top-10 largest streams, distinct/top event types, storage sizes (`mediatheca.db`, WAL sidecar, `images/` cache), and the **unknown-event report** (administration-gxd6e, below). Loads from one aggregate DTO, `HealthStats` (`IAdminApi.getHealthStats`), so the whole tab is a single round trip. The per-stream and per-event-type aggregates are index-only `GROUP BY` scans (`EventStore.getEventCountsByStream`/`getEventCountsByType`); the daily counts are bounded to the ~90-day window via an indexed timestamp range (`EventStore.getDailyEventCounts`) rather than scanning the whole table. See ADR-0021 for the full cost reasoning and the growth threshold at which this would need a materialized summary table instead.
- **Unknown-event report** (administration-gxd6e) — surfaces schema drift on the Health tab as two lists over `HealthStats.UnhandledEventTypes`/`UnformattableEventTypes` (each a `UnknownEventTypeRow list`: event type, count, one sample event's raw JSON), built from `EventStore.getEventCountsByType` (already scanned for the Health tab, no new query cost) plus one indexed point lookup per distinct type (`EventStore.getSampleEventForType`). Each BC's `Serialization` module now hand-declares `handledEventTypes: string list` — the same literal strings already appearing as `deserialize` match arms (F# pattern matches aren't reflectively introspectable, so this can't be derived, only kept in lockstep) — registered in `Administration.handledEventTypesByBoundedContext` alongside `boundedContextPrefixes`. Two **independent** checks per event type, run against one sample stored event: **unhandled** — the type's owning BC (resolved via stream prefix) doesn't list it in its `handledEventTypes`, or the prefix matches no known BC at all; **unformattable** — that sample event, run through `EventFormatting.formatEvent`, returns `None`. A type can land in neither, either, or both lists — e.g. before administration-qk3f7 closed it, `Game_rawg_id_set` was handled by `Games.Serialization.deserialize` but had no case in `EventFormatting.formatGameEvent` (unformattable but not unhandled), the one real handled-but-unformattable drift the report ever caught; `EventFormatting.formatGameEvent` now has a `Game_rawg_id_set` case, so `handled ⟺ formattable` holds for every real event type currently in the store. Display-only, not persisted.
- **Jobs tab** (the Jobs section of Settings' inline administration panel, `src/Client/Pages/AdminJobs/`) — durable history and manual triggering for the two `ScheduledJobs.JobSpec` entries (Steam playtime sync, Series TMDB refresh), per **ADR-0026**. Every fire — the daily timer or an operator's "Run now" — is recorded as a **job run**: a `job_runs` row (`job_name`, `trigger` = `scheduled`|`manual`, `status` = `running`|`ok`|`error`|`skipped`|`interrupted`, `summary`, `started_at`/`finished_at` — timestamps stored ISO-8601 UTC). The shared choke point is `ScheduledJobs.tryStartJob recorder spec trigger`, which claims a name-keyed in-memory guard (`runningJobs`, owned by the recorder's own closure — ADR-0035 — the same "name-keyed single-flight" shape as `AdminGuards.RebuildingProjections`, just closure-owned rather than record-owned since the recorder is already this state's natural per-instance home) and wraps the job body in a try/finally that **guarantees** the row reaches a terminal status — `ok`/`skipped` from a clean `JobRunOutcome`, `error` (with the exception message) from an uncaught exception — and always releases the guard slot; a second trigger of the same job name, from either source, is refused with no row written. **Run-now is fire-and-forget**: `IAdminApi.runJobNow` returns `RunJobStarted runId` (or `RunJobRejected`) *before* the job completes — a plain Remoting call, not SSE, since the tab just polls `getJobStatuses` (reusing ADR-0023's epoch-guarded polling `Cmd`) until the row resolves. **Crash reconciliation happens only at server startup** (`Administration.initializeJobRuns`, called before `ScheduledJobs.startAll`): any row still `running` at boot is definitionally orphaned (the in-memory guard is empty on a fresh process) and is marked `interrupted`; this never runs on a read path, since reading can't distinguish a live in-flight run from a crash. The **injected recorder seam** (`ScheduledJobs.JobRunRecorder`, implemented by `Administration.makeJobRunRecorder conn`) exists because `ScheduledJobs.fs` compiles before `Administration.fs` and must not depend on it — `Composition.fs` builds one recorder instance and passes it to both `ScheduledJobs.startAll` and `Administration.create`, so the scheduled timer and manual run-now share one guard and one connection. `SeriesRefresh.runNightlyJob` and `PlaytimeTracker.runSync` (Integration BC) return their natural result types; the `JobRunOutcome` mapping happens in `Composition.fs`'s job-body closures, not in the Integration modules themselves.
- **Table classification registry** (administration-t9bzx, **ADR-0044**) — `Administration.tableRegistry : (string * TableClass) list` classifies every durable table in `mediatheca.db` as exactly one of `Projected of projectionName` (checkpoint-tracked, rebuildable, drift-checked — the fifteen tables owned by the six registered `projectionHandlers`), `Cache of refreshedBy` (re-derivable from an external system's own state via a full clear-then-repopulate sync — the three `jellyfin_*` tables, refreshed by Jellyfin's sync handlers in `Api.fs`), or `Imperative of writtenBy` (written directly by a named module, outside both the projection catch-up path and any external re-sync, with no replay/re-fetch recovery if lost — `cast_members`/`movie_cast`/`series_cast`/`movie_crew` via `CastStore`, `game_journal_blocks` via `GameJournal`, `settings` via `SettingsStore`, `job_runs` via Administration's own job-runs recorder, and `game_play_session`/`steam_playtime_snapshot` via `PlaytimeTracker`). This replaces what used to be tribal knowledge encoded only as absence — scattered doc-comments explaining why a check omits a given table (ADR-0025's `tableExists` guard, ADR-0031's not-dirty guard) rather than one place stating positively what every table is. `projectionTables` (consumed by `buildProjectionStats`/`checkProjectionDrift`) is now derived from `tableRegistry` by filtering to `Projected` entries, so the two can no longer drift apart. `IAdminApi.getUnrebuildableTableStats` surfaces the `Cache`/`Imperative` half's row counts as its own section — additive, server-side only for now; client display is deferred. `steam_playtime_snapshot` carries a doc-comment noting it is really a sync cursor (not a true projection or cache) and that games-p6vkz is expected to delete this table outright once play sessions become logged events. `TableClassificationTests.fs`'s registry-coverage test asserts `tableRegistry` matches every non-`sqlite_*`/non-`events*`/non-`projection_checkpoints` table in a fully-initialized schema, so a table created anywhere without a matching entry fails a test instead of silently reproducing the blind spot that let `game_play_session` hold unrebuildable history unflagged for months.
- **Metadata cache tier** (administration-c3nvp, **ADR-0045**) — `MetadataCache.fs`, the durable, non-projection home for third-party descriptions that fail ADR-0043's re-derivability test: `game_metadata_cache` (typed columns mirroring `game_detail`'s RAWG/HowLongToBeat-sourced fields — `description`, `short_description`, `website_url`, `cover_ref`, `backdrop_ref`, `rawg_id`, `rawg_rating`, `hltb_hours`, `hltb_main_plus_hours`, `hltb_completionist_hours`) and `movie_metadata_cache` (just `movie_slug` + `fetched_at` — ships empty and unread, since Movies has no out-of-band metadata writer today; `movies-v2gkh` is the deferred cutover). Same shape as `ImageStore`/`JellyfinStore`: durable, slug-addressed, seeded once from the current projection snapshot. `MetadataCache.initialize` runs once at `Composition.buildApp` startup, beside `JellyfinStore.initialize`; `MetadataCache.seedFromProjections` runs after `Projection.startAllProjections` (so `game_detail` is guaranteed to exist), gated on a `SettingsStore` `metadata_cache_seeded` marker rather than a swallowed exception — a genuinely one-time copy, not an ongoing sync. Every `fetched_at` is nullable and starts `NULL`: "seeded from the projection, never actually fetched" is the cohort a first genuine refresh should prioritize. Both tables are registered `Cache` in `Administration.tableRegistry` (ADR-0044) — never checkpoint-tracked, never diffed by `checkProjectionDrift`, untouched by `Projection.rebuildProjection`. **Hard constraint, load-bearing**: no `ProjectionHandler` reads or writes this module — doing so would degrade ADR-0031's "read-only against live holds by construction" to a code-review property and let a nightly refresh race the drift check into false positives. This task stands up the tier and seeding machinery only; per-BC cutover (joining the cache at read time, narrowing the writing event, dropping the projection column) is separate follow-up work (`series-m7fdk`, `movies-v2gkh`, `games-a7dqx`).
- **Setting** — a configuration value persisted in `SettingsStore.fs`. API keys, sync cadence, Jellyfin URL, Steam credentials, etc.
- **Image ref** — a stable identifier for a stored image (posters, backdrops, friend avatars). The image store (`ImageStore.fs`) is the source of truth; aggregates reference images by ref.
- **Slug** — domain-stable identifier used across BCs (friend slug, movie slug, etc.). Generated by `Slug` module in Shared.
- **Playwright e2e harness** (`playwright.config.ts`, `tests/e2e/`, ADR-0027) — the project's first browser/e2e test harness, first exercised on the Events tab's Follow toggle. `webServer` drives the real dev stack via non-watch `dotnet run` (not `dotnet watch` — its child process tree orphans on Windows teardown), each run gets a fresh temp `DATA_DIR` (never the real dev DB), and "event appended elsewhere" is triggered via a direct Fable.Remoting HTTP call (`POST /api/{TypeName}/{Method}`, body = a JSON array of arguments even for one arg), not a raw event-store write or UI clicking. `getEventsAfter` traffic is observable via the vite-proxied `:5173` origin, not just `:5000`. Run via `npm run test:e2e`. Standing up the harness surfaced **administration-tj8n2**: the two `ScheduledJobs` catch-up timers raced on the shared `SqliteConnection` and could crash a freshly cold-started server — fixed for real by ADR-0028 (dedicated job connection + per-command lock), so the interim `MEDIATHECA_DISABLE_SCHEDULED_JOBS=1` e2e-only workaround is retired and jobs run unconditionally, same as every other environment. `event-tail-follow.spec.ts` (administration-a4d9b) codifies ADR-0023's three Follow-toggle behaviors as committed specs on top of this harness — arrival + `animate-highlight`, filter-respecting live rows, and all three no-orphan-polling sub-cases (toggle-off, pagination-away, and the load-bearing real client-side navigate-away that was previously only guarded by static review). Its specs originally triggered events sequentially, never concurrently, via `addFriend` — concurrent calls empirically crashed the shared connection (`SqliteConnection does not support nested transactions`), which motivated **administration-cx92m**'s request-concurrency audit (ADR-0030's interim gate) and **administration-mz6kp**'s per-request connection factory (ADR-0033) that superseded it; `addFriends` fires concurrently (`Promise.all`) and a dedicated repeated-burst test is the regression proof. It also surfaced **administration-nf3wk**: the event explorer's zero-filter-match state used to render `"No events found."`, the same message as a genuinely empty store, with `paginationBar`'s own `"No matches"` string left unreachable dead code given the `view` branch order. Resolved by `EventBrowser.State.emptyStateMessage`/`anyFilterActive` (`Model`'s six string filter fields), which now render `"No matches for the current filters."` distinctly whenever a filter is active; `paginationBar`'s dead branch was removed (it only ever renders once `model.Events` is non-empty, so `TotalMatches > 0` there). **administration-svq3t** established the suite's first destructive-spec precedent: `admin-surgery.spec.ts` covers the Surgery tab's edit/delete/rename flows plus the cross-tab dirty banner, and — because those flows mutate real `events` rows with no restore path yet (administration-n8kqw) — the whole `describe` block is gated by `test.skip(!process.env.CI, ...)`, the deliberate exact inverse of `playwright.config.ts`'s `reuseExistingServer: !process.env.CI`, so the gate and the reuse-hazard it guards against can never drift apart; any future destructive spec should inherit this same `process.env.CI` gate (a prose convention, not lint-enforced — ADR-0059). It also confirmed empirically that `IAdminApi`'s int64 fields (`GlobalPosition`, `StreamPosition`, e.g. from `getEventPage`) arrive over Fable.Remoting as **signed strings** (`"+0"`, `"+1"`), not JSON numbers — an undocumented `Fable.Remoting.Json`/`FableJsonConverter` encoding quirk; any spec reading these fields must `Number(...)`-normalize them before comparing against the plain-digit text the server renders in the DOM. **administration-k3vmt (ADR-0041)** dissolved the `/admin` console into inline sections on Settings: every spec above still navigates to its former `/admin/*` URL (all now resolving to `Settings`) but must additionally expand the section it needs before interacting with its content — sections start collapsed and unloaded — via a `#settings-admin-<name>` id locator (`adminSectionCard`/`expandAdminSection` in `admin-surgery.spec.ts`, `expandEventsSection` in the two Events specs); `admin-surgery.spec.ts`'s former `toHaveURL(/#\/admin\/projections$/)` assertion on the dirty banner's link became a DOM assertion (the Projections section's own checkbox becoming checked), since that link no longer navigates. A new spec, `settings-admin-sections.spec.ts`, covers what's specific to the dissolution: exactly one admin query (`getProjectionStats`) on a `/settings` visit, none at cold start elsewhere, load-once-on-first-expand with no refetch on re-expand, and the Events-section-collapse Follow-teardown trigger (ADR-0023's second trigger, alongside leaving Settings entirely).
- **Compensating-event composer** (administration-xjmda, **ADR-0032**) — the stream drill-in's "Append corrective event" action: the idiomatic event-sourcing fix for bad data is appending a corrective event, not mutating history (ADR-0002), and this is the safe path before any raw-surgery tooling exists (it `blocks` administration-wwc36, the escape hatch for when this pattern doesn't apply). The operator picks an event type from those seen anywhere under the stream's bounded-context prefix (`IAdminApi.getCompensatingEventTypes`, `EventStore.getDistinctEventTypesForPrefix`), pre-fills the payload by cloning the most recent real instance of that type — the target stream itself first, falling back BC-prefix-wide (`getCompensatingEventTemplate`, `EventStore.getMostRecentEventOfType`) — edits it, then previews and commits. **Validate-by-round-trip**: `Administration.eventCodecs` wraps each BC's own public `Serialization.serialize`/`deserialize` seam (no DU reflection, no template registry — see ADR-0032 for why both were rejected) as `deserialize eventType data |> Option.map serialize`, dispatched by stream-id prefix the same `if/elif StartsWith` way `EventFormatting.formatEvent` dispatches formatters. The bytes actually appended are the *re-serialized canonical form*, never the operator's raw edit; a payload that fails to deserialize is refused outright (no row inserted). `previewCompensatingEvent` reads the current `expectedPosition` and returns the canonical preview for the confirmation dialog; `appendCompensatingEvent` takes that same `expectedPosition` back as a caller-supplied value and re-validates independently before appending via `EventStore.appendToStream` (pure INSERT, expected-position concurrency-checked — never the explicit-rowid path `importNdjson` uses), then runs catch-up over every registered `projectionHandlers` entry, identical to `Api.executeCommandCore`'s idiom. Appended rows carry `metadata = {"source":"admin-console"}` — the one intentional, projection-invisible difference from an organic event. Like every other request-reachable transaction site, this runs on the connection `appendCompensatingEvent` opened for this one request (`use conn = factory ()`, ADR-0033) — no lock needed, since no other request shares that connection object. The confirmation dialog is a paper-overlay modal (ADR-0016, via `Components.ModalPanel`) showing the exact canonicalized payload about to be appended.
- **Event surgery** (administration-wwc36, **ADR-0034**) — the Surgery tab (the Surgery section of Settings' inline administration panel since ADR-0041, `src/Client/Pages/AdminSurgery/`): the raw-log escape hatch for cases the compensating-event composer (administration-xjmda, ADR-0032, which `blocks`-depended this task so the safe path always ships first) can't reach — a genuinely wrong-payload event, or a stranded event-type name left by a code-side DU rename. Three operations, **edit** (`UPDATE events SET data, metadata`), **delete** (`DELETE FROM events`), and **rename** (`UPDATE events SET event_type` store-wide), each behind the identical three-guardrail protocol: (1) **`VACUUM INTO` backup first**, on the op's own per-request connection (`use conn = factory ()`, ADR-0033), run in autocommit *before* any `BeginTransaction` (SQLite refuses `VACUUM` inside a transaction) — verified by opening the backup on a throwaway, unconfigured connection (never `configureConnection`, which would flip a plain file to WAL) and checking `PRAGMA integrity_check` + a row count; `VACUUM INTO`/verify failure aborts with **no row touched**, surfaced as the typed `SurgeryResult.BackupFailed reason` rather than an exception (mirrors `OrphanScan`/`PurgeResult`'s idiom); success carries `SurgeryResult.Applied(backupPath, affectedRows)`. (2) **Preview + explicit confirm** — `previewEventEdit`/`previewEventDelete` return the one targeted row by `global_position` (`SurgeryEventRow`, edit/delete's target; delete's preview additionally carries `StreamCurrentPosition` so the client can render the gap-consequence copy), `previewEventTypeRename` returns an exact `Count` plus a bounded `Sample`; every preview is a pure read, so cancelling (never committing) leaves `events`/`events_fts`/`projection_checkpoints` untouched by construction — confirmation is a paper-overlay modal (ADR-0016, `Components.ModalPanel`, same as the composer's). (3) **Projections-dirty signal** — the mutation, an `events_fts` `('rebuild')` resync (edit/delete only; rename doesn't touch `data` so needs none — reusing the exact idiom `EventStore.createFtsIndex`'s own backfill uses, since `events_fts` has only an `AFTER INSERT` trigger and never before had an UPDATE/DELETE path to cover), and a rewind of every checkpoint-tracked projection's checkpoint to 0 (`Projection.saveCheckpoint handler.Name 0L`) all share **one transaction** on the same connection (mutate-then-rebuild order, load-bearing for delete: the FTS rebuild must see the row already gone). `Administration.isAnyProjectionDirty` (ADR-0025, unmodified) then reports every handler dirty until the operator reruns Rebuild-all (administration-qjcp4, ADR-0024) — the same "leave dirty, reuse Rebuild-all" precedent ADR-0029 set for NDJSON import. **Delete leaves permanent `stream_position`/`global_position` gaps by design** (no renumbering) — verified safe against `appendToStream`'s fresh `MAX` re-read, `getMaxGlobalPosition`'s deliberate `MAX` (not `COUNT`), and the keyset/live-tail cursors' strict `</>` semantics. A **"projections out of sync — rebuild" banner**, rendered above all six administration sections on Settings regardless of which are expanded/collapsed (moved from above the tab bar of the old `/admin` shell by ADR-0041), is client-derived from `getProjectionStats`'s `Lag` field — no new API method; `Admin.State`'s `Surgery_msg` handler reloads `ProjectionsModel.Stats` immediately after every committed mutation so the banner reacts without waiting for a section revisit. Its "Go to Projections" affordance is an in-page expand+scroll (`Settings.State`'s `Go_to_projections_section`), not a navigation — per-section deep-linking was dropped by ADR-0041. **Backup retention is keep-all** — `backups/` (a sibling directory of the live db file, derived from `dbPath`) is never pruned by this feature; `getBackupStats` is a plain directory walk (`Count`, `TotalBytes`) feeding the Surgery tab's stats panel.
- **Admin guard ownership** (administration-jrflk, **ADR-0035**) — single-flight guards (`ConcurrentDictionary<string, unit>`-shaped claim/release state) in this BC are always **per-instance values owned by the composition root**, never module-level singletons: `Composition.fs` constructs each guard exactly once and threads it explicitly to every consumer (`AdminGuards` for the projection-rebuild/drift-check/wipe-import guards — the third field, `WipeImportInProgress`, added by administration-n8kqw/ADR-0038; the job-run recorder's own closure for `runningJobs`). A module-level guard is invisible-but-wrong in a single-process server (there's only ever one), yet silently shared across the whole Expecto test assembly, where parallel test files can collide on a name neither knows the other uses. The next admin feature adding a guard should follow this pattern from the start, not rediscover it.
- **Per-request connection factory** (administration-mz6kp, **ADR-0033**, supersedes administration-cx92m's ADR-0030) — every request/SSE operation opens and disposes its own `SqliteConnection`, retiring the single shared request-serving `conn` ADR-0030's interim `requestDbLock` gate used to guard. `Composition.buildApp` builds `connectionFactory : unit -> SqliteConnection` (`Composition.createConnectionFactory`) — pragmas re-applied on every open via `EventStore.configureConnection`, table/FTS creation staying a one-time step on the separate bootstrap `conn`. `Api.create`/`Administration.create` take this factory instead of a live connection; every record member opens exactly one `use conn = factory ()` inside its own `async`/`task` scope (never a bare `let`, never a `use` outside the async scope — either leaks the connection past the request), and multi-append members (`removeMovie`, the Steam/Jellyfin import loops) hold that one connection across every append they make. The five raw Giraffe SSE handlers (`Api.steamFamilyImportHandler`, `Administration.exportEventsStreamHandler`/`importEventsStreamHandler`/`projectionRebuildStreamHandler`/`driftCheckStreamHandler`) each open one connection for the whole stream, not per DB call. `JellyfinSync.triggerSync`'s background sync (genuinely detached via `Async.Start`, so it can't borrow a request-scoped connection) opens its own connection *inside* the spawned background async instead. This closes the residual read×write/read×read race ADR-0030 explicitly left open, by removing the shared mutable connection object entirely rather than locking around it — safe per ADR-0028's finding that WAL + `busy_timeout` serialize writes at the *file* level across separate connections (proven first for the dedicated job connection, generalized here to one connection per request). ADR-0028's `jobConn`/`jobDbLock` and the vestigial `manualSyncTriggerLock` are unaffected — they guard a different connection object for a different reason. `tests/Server.Tests/TestDb.fs` (`TestDb.withTempDbFactory`) is the shared per-test, file-backed fixture the affected test files now build on (not shared-cache `:memory:`, which doesn't exercise WAL's file-level serialization and is destroyed when its last connection closes).

## Aggregates

No domain aggregates. The store and registry tables are infrastructure.

## Key events

The event store **carries** events from every BC but does not own a stream of its own. There is no `Administration_*` event family.

## Key commands

Operational: "rebuild projection X", "set setting Y", "save image Z". These are command-shaped but not in the same sense as core BC commands.

## Relationships with other contexts

- **Shared kernel** with every BC: the event store and image store are consumed everywhere.
- **Supports:** Integration (settings live here, adapters read them).

Frontend tasks in this BC (event browser, settings UI) **must** `depends_on` the design-system styleguide task. See [[design-system]].
