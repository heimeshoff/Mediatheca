# Research: Automating Steam `IFamilyGroupsService` auth (SteamKit2 QR login / refresh tokens vs. browser-scraped `access_token`)

## Question

Mediatheca's server currently requires the user to manually scrape a Steam family web `access_token` from Chrome DevTools roughly every hour to call the undocumented `IFamilyGroupsService` endpoints (`GetFamilyGroupForUser`, `GetSharedLibraryApps`, `GetFamilyGroup`). Can this be replaced with a one-time interactive login (SteamKit2 QR code or credentials) that yields a refresh token, from which the server mints its own access tokens via plain HTTP — with **no live SteamKit2 CM connection needed at refresh time**? And critically: does a token minted this way actually carry the right audience/scope to authorize the family endpoints, or do those endpoints specifically require the browser's own JS-minted token?

## Summary

- SteamKit2 has an official QR-login sample (`Samples/001_AuthenticationWithQrCode`) using `SteamClient.Authentication.BeginAuthSessionViaQRAsync()` → `AuthSession.PollingWaitForResultAsync()`, which returns an `AccessToken` and `RefreshToken`, plus an `IsPersistentSession` flag on `AuthSessionDetails` to request a long-lived refresh token [1][7].
- Whether the auth handshake itself needs a live binary CM connection depends on `AuthSessionDetails.PlatformType`: SteamKit2/node-steam-session route `SteamClient`-platform sessions over the binary CM (WebSocket) transport, but **non-`SteamClient` platform types (`WebBrowser`, `MobileApp`) are routed over a plain HTTPS `WebApiTransport` hitting `api.steampowered.com/IAuthenticationService/...`** — no persistent CM connection required for the auth handshake itself [3][4]. The official SteamKit2 sample happens to call `steamClient.Connect()` first, but that's because the sample subsequently does a full `SteamUser.LogOn()` into the Steam network, which does need CM — that's a separate concern from the QR handshake.
- Refreshing an access token from a stored refresh token via a plain `GenerateAccessTokenForApp` HTTP POST **works only for `MobileApp`-platform refresh tokens as of the library's current behavior**; `WebBrowser`-platform refresh tokens get `AccessDenied`, and as of an April 30, 2025 Steam-side change, `SteamClient`-platform tokens now require the refresh to happen over an **authenticated** CM connection (`CMsgClientLogon` first, then the `Authentication.GenerateAccessTokenForApp#1` unified message on that connection) [2][5]. This is a load-bearing, dated fact — it directly kills the "plain HTTP, no SteamKit2 dependency at refresh time" plan for `SteamClient`-flavored tokens, but not necessarily for `MobileApp`-flavored ones.
- Refresh token lifetime is reported around **1 year**, with access tokens minted from it lasting ~1 day, but Valve can and does invalidate tokens server-side independent of the JWT's `exp` claim for undocumented reasons (IP changes are suspected but not confirmed) [6][8].
- **Q4 (decision-critical) is not confirmed by any public source found.** No community writeup, GitHub repo, or forum thread describes successfully calling `IFamilyGroupsService/*` with a SteamKit2- or refresh-token-derived access token. The two concrete, working community implementations found (Chachigo's `FamilyBot`, a C#-adjacent devlog-documented bot; and its predecessor) **both exclusively use a browser-scraped token** (`store.steampowered.com/pointssummary/ajaxgetasyncconfig`'s `webapi_token`) via Selenium automation, with the author explicitly stating "there is no other way to get the Steam token than getting it with a browser that is connected to the Steam account" [9][10]. This is circumstantial (could mean "the author didn't try" rather than "it's impossible"), not proof, but it's the strongest available public signal and it points against the plan working out-of-the-box.
- SteamKit2 NuGet is a modern, actively maintained .NET library (targets .NET, cross-platform); no reported .NET 9 incompatibility was found in this research pass, but this specific claim is unconfirmed by direct testing — see Open Questions.

## Findings

### 1. SteamKit2 QR login API and CM-connection requirement

The official SteamKit2 sample repo ships two relevant samples: `Samples/000_Authentication` (credentials-based) and `Samples/001_AuthenticationWithQrCode` (QR-based) [1][7]. The QR sample's flow:

```csharp
steamClient.Connect();
// ... in OnConnected callback:
var authSession = await steamClient.Authentication.BeginAuthSessionViaQRAsync( new AuthSessionDetails() );
Console.WriteLine( $"Challenge URL: {authSession.ChallengeURL}" );
authSession.ChallengeURLChanged = () => { /* redraw QR */ };
var pollResponse = await authSession.PollingWaitForResultAsync();
steamUser.LogOn( new SteamUser.LogOnDetails {
    Username = pollResponse.AccountName,
    AccessToken = pollResponse.RefreshToken,
} );
```

Key classes/methods confirmed: `SteamClient`, `SteamClient.Authentication` (an `SteamAuthentication` handler), `AuthSessionDetails`, `BeginAuthSessionViaQRAsync(AuthSessionDetails)` → `QrAuthSession`-like object exposing `ChallengeURL` / `ChallengeURLChanged`, and `PollingWaitForResultAsync()` on the session, which resolves to an object exposing `AccountName`, `AccessToken`, and `RefreshToken` [7]. The credentials-based sibling sample (`000_Authentication`, mirrored by the third-party `SteamDesktopAuthenticator` tool) uses the analogous `BeginAuthSessionViaCredentialsAsync(AuthSessionDetails)`, with `AuthSessionDetails` fields including `Username`, `Password`, `IsPersistentSession` (bool — the "remember me" flag that requests a long-lived refresh token), `PlatformType` (an `EAuthTokenPlatformType` enum), `ClientOSType`, and an `Authenticator` callback for 2FA [11]. A Go port of SteamKit2's protocol (`go-steam`) documents `AuthSessionDetails.ShouldRememberPassword` as the literal equivalent of SteamKit2's `IsPersistentSession`, confirming the field is real and semantically "get me a persistent/long-lived refresh token" [12].

**On the CM-connection question**: transport for the *auth handshake itself* is platform-type-dependent, not universally CM-bound. Per node-steam-session's documented design (which mirrors SteamKit2's own protocol/transport split, since both consume the same `IAuthenticationService` protobufs): "For the SteamClient platform type, a WebSocketCMTransport will be used to communicate with a CM server... For other platform types, a WebApiTransport will be used to interact with the Steam login server using api.steampowered.com" [3][4]. That means if `AuthSessionDetails.PlatformType` is set to `WebBrowser` or `MobileApp` rather than `SteamClient`, the QR/credentials handshake itself is plain HTTPS against `IAuthenticationService/BeginAuthSessionViaQR(Credentials)`, `PollAuthSessionStatus`, etc. — **no live CM socket needed for the login handshake**, only for subsequent full "log on to Steam's network" activity that this app doesn't need [3]. The official SteamKit2 QR sample connects the CM client anyway, but that's an artifact of the sample also demonstrating a full `SteamUser.LogOn()`, not a hard requirement of `BeginAuthSessionViaQRAsync` per se — this inference is drawn from the transport-selection behavior documented for the sibling library, not from a SteamKit2-specific statement, so treat it as **likely but not independently confirmed for SteamKit2 itself**.

### 2. Refreshing an access token from a stored refresh token — plain HTTP or not?

`https://api.steampowered.com/IAuthenticationService/GenerateAccessTokenForApp/v1/` is a real, documented-by-community endpoint that, "given a refresh token for a client app audience..., generates an access token" [2]. Whether it can be called with a bare HTTP POST (no SteamKit2, no CM) depends on the refresh token's platform/audience:

- **`MobileApp`-platform refresh tokens**: node-steam-session's `refreshAccessToken()` (which wraps a plain HTTPS call to `GenerateAccessTokenForApp`) is reported to work for `EAuthTokenPlatformType.MobileApp` as of a 2025-04-30 community status note [2].
- **`WebBrowser`-platform refresh tokens**: reported to fail with `AccessDenied` on this same plain-HTTP path [2].
- **`SteamClient`-platform refresh tokens**: also fail with `AccessDenied` **unless the refresh is performed over an authenticated CM connection** — per Dr. McKay (author of node-steam-session/node-steam-user) on the library's support forum, as of an April 30, 2025 Steam-side change, "access token refreshes for SteamClient tokens are authenticated now," meaning the client must log on over an *unauthenticated* CM connection using the refresh token via `CMsgClientLogon`, and only then send the `Authentication.GenerateAccessTokenForApp#1` unified message on that now-authenticated connection [5]. This is dated (2025-04-30 through 2025-05-12 forum activity) and describes a real behavior change on Valve's side, not a library limitation — so it should transfer to SteamKit2 usage of `SteamClient`-platform tokens too, though this wasn't independently verified against SteamKit2 source in this pass.
- A separate, resolved forum thread about `GenerateAccessTokenForApp` returning `{"response":{}}` (empty) found that the fix was ensuring the refresh token's `aud` (audience) claims included `"mobile"` alongside `"web"`, `"renew"`, `"derive"` — i.e., **the refresh token minted at login time carries fixed audience claims tied to the platform type chosen at login, and `GenerateAccessTokenForApp` is picky about which audiences it will act on** [2].

**Implication for Mediatheca**: to get "mint fresh access tokens via plain HTTP with no SteamKit2 dependency at refresh time," the one-time interactive login should be done with `AuthSessionDetails.PlatformType = MobileApp` (not the default/`SteamClient`), producing a refresh token whose audience includes `web` + `mobile`. This appears to be the only path in current community evidence that supports refreshing over plain HTTP without an authenticated CM connection. This has **not been tested against SteamKit2 specifically** in this research pass — evidence is from node-steam-session (JS), which speaks the same wire protocol but is a separate codebase.

### 3. Refresh token lifetime and invalidation

- A refresh token is reported valid for about **1 year**; access tokens minted from it are valid for about **1 day** [6][GitHub issue #1125 community summary].
- `IsPersistentSession` / `ShouldRememberPassword` at login time is what requests the long-lived token; without it, tokens are shorter-lived (analogous to the ~207-day "remember password" web JWT cookie vs. the ~1-day plain session cookie noted in the same source) [6].
- Renewal rotates the token: "If a refresh token is successfully renewed, the old refresh token will become invalid, even if it is not yet expired" [4] — so a naive "renew on every use" strategy is safe but requires persisting the *new* token each time, not reusing a fixed one.
- Server-side invalidation is possible independent of the `exp` claim. Direct quote from the library maintainer: "tokens can be invalidated server-side at Valve's discretion, and nobody's sure exactly what makes that happen besides IP changes" [8]. This means an ADR built on this approach must plan for a re-auth fallback path (email/notify the user to re-scan a QR code), not assume the token is good until its stated expiry.
- Password changes, Steam Guard changes, and explicit revocation (`RevokeToken` API, or user hitting "sign out of all devices") are the expected invalidation triggers, though the *complete* list of triggers is explicitly stated by the maintainer as not fully known [8].

### 4. Audience/scope for `IFamilyGroupsService` — the decision-critical unknown

This is genuinely **not confirmed by any public source found** in this research pass, in either direction. What is known:

- Steam's modern (post-October-2022) access tokens are JWTs with an `aud` (audience) claim that varies by the `PlatformType` used at login: `SteamClient` → `["web","client"]`, `WebBrowser` → `["web"]`, `MobileApp` → `["web","mobile"]` [3]. Since October 2022, "web session cookies are now access tokens that can also be used to authenticate with parts of the Steam WebAPI" [community summary, GitHub issue #1125] — i.e., the mechanism by which the browser's own `access_token` (that Mediatheca currently scrapes) authorizes WebAPI calls is exactly this JWT-with-`aud`-claim scheme, not something categorically different.
- This strongly suggests that a token with `"web"` in its `aud` claim — obtainable via `MobileApp`- or `SteamClient`-platform login — is *structurally* the same kind of artifact the browser scrape currently produces, and should in principle be accepted the same way by any WebAPI endpoint gated only on "has a valid `web`-audience access token."
- However: **no source found reports actually trying this against `IFamilyGroupsService` and succeeding.** The one concrete, documented, real-world family-library sync tool found — Chachigo's `FamilyBot` (a Discord bot notifying on new family-shared games, functionally the same problem Mediatheca has) — uses exclusively browser-scraped tokens via Selenium automation of a live Firefox profile signed into Steam, explicitly because (per the author) "there is no other way to get the Steam token than getting it with a browser that is connected to the Steam account" [9][10]. The author does not describe having tried SteamKit2 or a refresh-token-derived token and hit a specific audience/scope rejection — the statement reads as "I didn't find another way," which is weaker evidence than "I tried X and X failed with error Y," but it is nonetheless the closest real data point available, and it is a negative signal.
- It's plausible (not confirmed) that `IFamilyGroupsService` specifically requires additional claims beyond a bare `"web"` audience — e.g., some Steam family-sharing endpoints are known (per the Steamworks partner "Steam Families" doc and steamapi.xpaw.me's auto-generated interface list) to be gated in ways not fully captured by public reverse-engineering docs, since the interface is explicitly undocumented by Valve [Steamworks partner docs; steamapi.xpaw.me]. Neither of those two official/quasi-official sources exposes per-method auth requirements for `IFamilyGroupsService` methods specifically (the partner doc doesn't cover this interface at all; steamapi.xpaw.me lists the interface but the fetched content didn't surface method-level auth notes) [13][14].
- **Recommendation for the spike**: this is empirically testable in under an hour — do the QR login with `PlatformType = MobileApp`, mint an access token via `GenerateAccessTokenForApp`, and call `GetFamilyGroupForUser` with it. If it 401/403s where the browser-scraped token succeeds, that's a definitive, cheap answer; no further literature search will substitute for that one test. This should be the first thing the spike does, before investing in the full QR-login UX.

### 5. SteamKit2 on .NET 9

No specific incompatibility reports were surfaced for SteamKit2 on .NET 9. The GitHub NuGet package listing shows SteamKit2 as an actively released, cross-platform .NET library [1]; the sample projects target modern .NET SDK-style csproj files. This claim should be treated as **weakly supported** (absence of reported problems, not a positive compatibility statement) — the spike should simply add the package and build to confirm, which is cheap and decisive.

## Open questions

- **The core Q4 answer remains unconfirmed either way.** No source directly states "a SteamKit2/refresh-token-derived `web`-audience access token does/doesn't work against `IFamilyGroupsService`." The one relevant data point (FamilyBot) is negative-leaning but weak (absence of evidence, not evidence of failure). **This must be resolved empirically** — the spike's very first step should be: QR-login with `PlatformType=MobileApp`, call `GenerateAccessTokenForApp`, hit `GetFamilyGroupForUser` with the result, and compare against the known-good browser-scraped token. This is a ~30-minute test that fully de-risks the rest of the spike.
- Whether SteamKit2's `BeginAuthSessionViaQRAsync`/`PollingWaitForResultAsync` truly avoid needing `steamClient.Connect()` when `PlatformType` is set to `MobileApp` or `WebBrowser` was inferred from node-steam-session's documented transport-selection behavior, not verified directly against SteamKit2's own source (repeated attempts to fetch SteamKit2's internal transport-selection source file 404'd; GitHub code search required authentication not available to this session). Worth a direct source read or a quick spike test.
- The precise, complete list of refresh-token invalidation triggers (beyond password change / explicit revoke / suspected IP change) is explicitly described by the community as unknown even to library maintainers — plan the ADR around "assume it can silently die, have a cheap re-auth path" rather than a specific trigger list.
- SteamKit2-on-.NET-9 compatibility was not stress-tested by this research pass, only inferred from absence of reported problems; confirm via a trivial `dotnet add package SteamKit2 && dotnet build` in the spike.
- Not investigated: whether `MobileApp`-platform login (as opposed to `SteamClient`) changes anything about the account's visible "logged in from a new mobile device" notifications/Steam Guard emails the user would see — worth checking during the spike since it affects the "one-time interactive login" UX story.
