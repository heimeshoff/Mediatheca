# Research: RomM vs. Mediatheca — games capability gap analysis

## Question

RomM (self-hosted ROM/retro-game library manager and browser-based emulator, github.com/rommapp/romm, docs.romm.app) and Mediatheca's Games bounded context both track video games for a self-hosted, single-user setup. What does RomM do that Mediatheca does not — grouped by theme, tagged with rough relevance to Mediatheca's vision — and, briefly, what does Mediatheca do that RomM doesn't?

## Summary

- **Category mismatch is the headline finding.** RomM is a ROM file server + in-browser emulator for legally-gray retro game files it stores and serves; Mediatheca's Games BC never touches game binaries — it is a catalogue/journal over *owned* (mostly Steam) games, recording status, play sessions, and metadata. Most of RomM's file-serving, emulation, and sync surface is **out of scope** for Mediatheca by design, not by gap.
- **Where the two do overlap** (external metadata enrichment, one title = one library entry, personal rating/notes, collections, play-time tracking) Mediatheca already covers the conceptual ground, just against a different data source (Steam/RAWG vs. IGDB/ScreenScraper/hashes) and without RomM's breadth of provider fallback-priority configuration.
- **Multi-user / permissions / OIDC / API tokens** are real gaps but tagged **out of scope** — Mediatheca is explicitly single-user, no-auth (CLAUDE.md).
- **RetroAchievements integration is a real gap, but Mediatheca already does *some* Steam achievement tracking** — corrected after review: `src/Server/Steam.fs` calls Steam's `ISteamUserStats/GetPlayerAchievements/v1` and `GetSchemaForGame/v2` endpoints, and the Games dashboard tab has a live "Recent Achievements" card (`src/Client/Pages/Dashboard/Views.fs`, `src/Shared/Shared.fs`'s `SteamAchievement`/`SteamRecentAchievementsQuery`/`getSteamRecentAchievements`). The actual, narrower gap is: no RetroAchievements-network integration (RomM's provider, covering ROM/retro titles Steam doesn't), no *persisted* or event-sourced achievement history (Mediatheca's card is a live API pull with a 5-minute in-memory cache, scoped to recently-played games only — nothing survives a cache expiry or appears in the Journal), and no per-game achievement list/completion percentage on the game detail page (only a dashboard "recent unlocks" feed).
- **Companion/handheld sync apps (Argosy, Grout, Playnite plugin)** are file-sync/launcher tooling tied to ROM ownership; not applicable without ROM hosting.
- **Physical game barcode scanning, jukebox/soundtrack player, DOS/PICO-8 players** are all emulation/file-serving-adjacent and out of scope. (Netplay is also out of scope, but corrected after review: it is not a 5.3.0 feature — a Netplay troubleshooting doc already existed at RomM 4.9.0, so it predates 5.3.0 by multiple versions; see Open questions for how early it actually shipped.)
- The reverse direction (what Mediatheca has that RomM doesn't) is a short list: cross-media journal/dashboard unifying movies/series/games/books, event-sourced history with full replay, In Focus intent-signalling, friends/played-with/family-owner social modeling, and Steam-Deck-compatibility + play-facet derivation — none of which RomM, as a single-domain ROM tool, attempts.

## Findings

### 1. What RomM is, in one paragraph

RomM ("A beautiful, powerful, self-hosted ROM manager and player") scans a filesystem library of ROM files organized by platform folder, computes file hashes (CRC32, MD5, SHA1, plus RetroAchievements-specific hashes), and matches those files against configurable metadata providers in a default priority order — IGDB > MobyGames > ScreenScraper > RetroAchievements > LaunchBox > ES-DE gamelist.xml > Hasheous > Flashpoint > Steam > HowLongToBeat, per `config.example.yml` [15] — enriching the resulting catalogue with cover art, descriptions, and achievement data [1][2][9]. It then lets the (potentially multi-) user play those files directly in the browser via EmulatorJS/Ruffle/js-dos, sync saves and states across devices, download/upload ROMs, and organize everything into standard, smart, and virtual (auto-generated, metadata-driven) collections [1][3][4]. Latest stable at time of writing is 5.3.0 (2026-09-21), with 5.3.1 following two days later (2026-09-23) [5]. Licensed AGPL-3.0, "free forever," no tracking [1].

### 2. Library scanning, filesystem layout, hashing

- **Folder-per-platform scan.** RomM expects a `roms/` (or configurable) root, one subfolder per platform, and as of 5.3.0 supports an explicit "custom library structure" mode as an alternative to automatic folder-name detection [5]. Scan modes include full, "New Platforms" (unscanned folders only), "Quick" (skip already-catalogued ROMs), and "Unmatched" [6].
- **Hashing pipeline.** Every file gets CRC32/MD5/SHA1 (plus RA-specific hashes) computed at scan time; the first metadata provider to recognize the file by hash or filename wins the initial match, with other providers layered in afterward for extra fields (achievements, HLTB, alt art) [6][2]. A live GitHub issue (#4167, "Romm not verifying roms correctly — poor SHA-1 consistency") suggests this hash-matching pipeline is imperfect in practice — single-source/anecdotal, flagged as such [7].
- **Hasheous** is a free, open-source, hash-based metadata provider that additionally proxies IGDB data and can resolve RetroAchievements IDs for matched games [2].
- **Gap tag:** **out of scope**. Mediatheca has no filesystem-scanning concept for games at all — it never stores or indexes game binaries; a "Game" is a metadata + playtime record keyed to a RAWG id and/or Steam appId (`.agentheim/knowledge/contexts/games/README.md`). Hashing/file-identification has no analog need.

### 3. Metadata providers and platform coverage

- RomM supports 400+ platforms and pulls from IGDB, ScreenScraper, MobyGames, RetroAchievements, Hasheous, LaunchBox, ES-DE gamelist.xml, Flashpoint, and HowLongToBeat, each with configurable per-field priority (e.g., cover-art source vs. description source can differ) [2][9]. 5.3.0 (2026-09-21) added Steam, Demozoo, Pouët, and CSDb as further metadata sources, plus SteamGridDB for artwork and per-field artwork-priority overrides (5.1) [5][1]. **Corrected after review:** the 4.5.0 metadata-providers doc and the 5.1.0 first-scan doc describe *that* priority is configurable but do not themselves state a default order. The default order is set in `examples/config.example.yml`'s `scan.priority.metadata` list, confirmed directly from that file: `igdb` (highest) → `moby` → `ss` → `ra` → `launchbox` → `gamelist` → `hasheous` → `flashpoint` → `steam` → `hltb` (lowest) [15].
- **Gap tag:** **aligned but narrower, not absent.** Mediatheca's Games BC already does provider-based enrichment — RAWG (canonical metadata/identity card: name, year, cover, genres) plus Steam (facets, Deck compatibility, release date, description) and HowLongToBeat (hours) — but with a fixed two-source model, not RomM's configurable N-provider priority stack, and with no equivalent of ScreenScraper/MobyGames/LaunchBox for the retro/emulation-specific catalog RomM targets. This is a difference of domain (owned digital-storefront games vs. ROM-identified retro titles) more than a missing feature.

### 4. In-browser emulation, save states, ROM patching, netplay, streaming

- **EmulatorJS + Ruffle (Flash) baked in**, "no setup required," for playing supported systems directly in the browser [1][3]. 5.3.0 added js-dos (DOS games) and PICO-8 cartridge support. **Corrected after review:** "emulator streaming" itself is not new in 5.3.0 — that release shipped a "massive update to emulator streaming... emulator streaming V2," reconfiguring it to one entry per container instead of one per emulator, plus memory-card syncing [5][18]; streaming existed at least as early as 5.1 (source 5's original summary) and possibly earlier — the exact introduction version wasn't tracked down (see Open questions).
- **Save/state sync across devices with conflict resolution** [1][3].
- **ROM Patcher** — apply stored or uploaded romhacks/translations on the fly [1]. **Corrected after review:** 5.0 did not introduce ROM patching — it **moved an existing patcher to the server**. 5.0's own release notes: "We've unlocked the full power of ROM patching by moving it to the server. Simply apply patches to your ROMs, now with the option to use stored or uploaded patch files" [18] — implying a client-side or otherwise more limited patcher predates 5.0; how far back it goes wasn't investigated (see Open questions).
- **Netplay** (EmulatorJS-based) — host/join a room, up to 4 players depending on core, requires config.yml-level enablement and STUN/TURN (ICE) servers for cross-network play; all players need an account on the instance, and netplay does not federate across instances [8]. **Corrected after review:** netplay is not a 5.3.0 feature — a troubleshooting doc for it already existed at RomM 4.9.0, so it shipped several minor versions earlier; the exact introduction version is unconfirmed (see Open questions).
- **Gap tag:** **out of scope**. None of this has an analog in Mediatheca's problem statement (a "personal media diary and intelligence hub," vision.md) — Mediatheca does not play or stream any media, it only tracks the fact that the user engaged with it (a watch/play session), sourced from Steam's playtime API or manual entry.

### 5. Multi-user, permissions, OIDC, API tokens

- **Corrected after review — the 4.9.0-era "scope-based roles, no custom roles" model is stale.** RomM's current (5.0+) permission model is **roles + permission groups**, not the older roles-are-a-scopes-convenience-layer model: there are two roles (Admin, which bypasses permission groups entirely including user management and tasks, and User, which operates within its assigned group). **Permission groups are user-creatable/customizable templates** defining read/write/delete access per entity type (platforms, ROMs, collections, firmware, assets, devices, users, tasks, logs) — "a missing grant means denied." On top of group assignment, admins can **grant/revoke individual capabilities per user** as one-off overrides. Exactly one group is the server-wide default, auto-applied to new users from invites, OIDC registration, or admin creation without an explicit group [19]. This "per-user and per-group permissions, with one configurable default group for new users. Tri-state grant/revoke on top of the group, and per-entity overrides" model shipped in 5.0 (July 2026), per that release's own notes [18]. The 25-Client-API-Token-per-user limit is still current and unchanged [10][19].
- **OIDC SSO** supported with documented guides for Authentik, Authelia, and (per README) Keycloak-style providers [1][11].
- **Gap tag:** **out of scope by explicit design.** CLAUDE.md: "Single-user app — no authentication." Not a capability gap so much as a different target user.

### 6. Collections

- Three collection kinds: user-curated **standard collections**, rule-based auto-populating **smart collections**, and **virtual collections** — auto-generated groupings over IGDB metadata dimensions (collections/series, franchises, genres, companies, modes), sourced from a `roms_metadata` view that coalesces manual + provider metadata, with low-count groups suppressed [12][3].
- **Gap tag:** **aligned, partial.** Mediatheca's Curation BC already has user-created Catalogs (ordered lists of MovieRef/SeriesRef/GameRef) and ContentBlocks (context-map.md), functionally close to RomM's "standard collections." Mediatheca has **no smart/rule-based or virtual/auto-generated collections** for games (or any media type) — that is a genuine feature gap, tagged aligned (fits the "intent-driven, auto-managing" design principle already stated in vision.md) but unbuilt.

### 7. RetroAchievements

- RomM surfaces RetroAchievements data as one of its metadata providers/overlays, tracking accomplishments per game [1][2][9].
- **Gap tag:** **tangential — corrected after review, this is narrower than first written.** Mediatheca is **not** achievement-blind: `src/Server/Steam.fs` (lines ~658–761) calls Steam's own `ISteamUserStats/GetPlayerAchievements/v1` and `GetSchemaForGame/v2` endpoints (`getPlayerAchievements`, `getGameSchema`, `getRecentAchievements`, the last wrapped in a 5-minute in-memory cache); `src/Shared/Shared.fs` carries a first-class `SteamAchievement` type, an `AchievementItems`/`SteamRecentAchievementsQuery` dashboard-card case, and a `getSteamRecentAchievements` RPC method; `src/Server/Api.fs` wires the endpoint through; and `src/Client/Pages/Dashboard/Views.fs` renders a live, expandable "Recent Achievements" card on the Games dashboard tab (icon, name, description, unlock time, per achievement). The real, narrower gap versus RomM is: (a) no **RetroAchievements**-network integration at all (RomM's provider — relevant to ROM/retro titles Steam doesn't cover), and (b) Mediatheca's achievement surface is **ephemeral and dashboard-only** — a live API pull scoped to recently-played games, 5-minute cache, no event-sourced or otherwise persisted history, and no per-game achievement list/completion-percentage view on the game detail page (unlike play sessions, HLTB comparison, or Deck compatibility, which are all first-class, queryable, per-game facts). So "aligned" is a better tag than "tangential" for the completion-percentage/per-game-history piece specifically, since Mediatheca already has the analogous engagement-signal pattern (HLTB-vs-playtime, Deck-compat) it could extend; RetroAchievements-network coverage itself stays tangential (targets ROM titles Mediatheca's Steam-centric catalogue mostly doesn't hold).

### 8. Companion apps and device sync

- **Argosy** — Android launcher, browse/launch the RomM library on handhelds/phones [1][13].
- **Grout** — first-party companion for muOS/NextUI Linux-based handhelds; bidirectional sync of ROMs, saves, and states over Wi-Fi, scheduled on idle/session-end/cron, superseding the older standalone muOS app [13].
- **Playnite plugin** — imports the RomM library into Playnite (Windows game-library manager) so ROMs appear alongside Steam games; installing in Playnite downloads the file from RomM [13].
- **Gap tag:** **out of scope**. These exist to move ROM files onto devices that run local emulator cores; Mediatheca has no files to move.

### 9. Downloads, uploads, physical games, jukebox

- ROM **download/upload** through the web UI, multi-file range-request downloads (5.1) [1][9].
- **Physical games support** — barcode or by-name lookup (against a UPC database, `UPC_LOOKUP_API_KEY`) for a game owned on cartridge/disc with no ROM file, matched to metadata like any other game — confirmed directly against the 5.3.0 GitHub release notes (2026-09-21) [5].
- **Jukebox player** — "a soundtrack player for your whole library that follows you as a mini player anywhere in the app," browse by album/platform/artist/genre, curated playlists (Free Radio, Decade Mix) — confirmed directly against the 5.3.0 GitHub release notes [5]. **Resolved after review** (open question closed): 5.0's own release notes confirm a smaller predecessor feature — "Music files stored within a ROM's `soundtrack` folder can now be played directly from the details page, and queried directly from the API" [18] — i.e. 5.0 added per-ROM soundtrack-folder playback on the detail page; 5.3.0's Jukebox is a materially bigger step (library-wide mini player, cross-library browsing by album/platform/artist/genre, curated playlists), not the same feature.
- **Gap tag:** physical-games barcode/UPC scanning is the one item worth flagging as **tangential** — it's a "catalogue a thing you own, without a digital file" pattern conceptually close to how Mediatheca catalogues books/movies by external id rather than a file. Downloads/uploads and jukebox are **out of scope** (file-serving).

### 10. Firmware/BIOS management

- Users upload/organize BIOS/firmware files per platform (`bios/{platform}` layout by default); RomM explicitly does not ship games or firmware and the team does not help source BIOS files [14].
- **Gap tag:** **out of scope** — purely an emulation-support concern.

### 11. API

- RomM exposes an API consumed by its own companion apps and third-party integrations (Playnite plugin, Grout, custom scripts), authenticated via per-user Client API Tokens [10][13].
- **Gap tag:** **out of scope for the same reason as multi-user** — Mediatheca is Fable.Remoting RPC for its own SPA only (`IMediathecaApi`, CLAUDE.md); no public/companion API surface exists or is implied by the vision.

### What Mediatheca has that RomM does not (framing only)

- **Cross-media unification.** One dashboard, one event store, one "In Focus" intent model spanning movies, series, games, and books — RomM is single-domain (retro games only).
- **Event-sourced replayable history** (ADR-0002) with a full admin console (event browser, projection rebuild, health/lag dashboards) — RomM is a conventional CRUD app over a relational store with scan-time enrichment, not an append-only event log.
- **Social/relationship modeling**: friends, "played with," family ownership of a shared game, recommended-by — RomM's multi-user model is about *access control to one shared library*, not *tracking who you personally experienced a game with*.
- **Derived-comparison intelligence**: HowLongToBeat-vs-actual-playtime, Steam Deck compatibility badges, play-facet (solo/co-op/versus/VR) derivation from Steam store categories — bespoke engagement analytics RomM has no equivalent of.
- **Journal/diary framing**: play sessions as calendar-day events feeding a cross-media activity heatmap — RomM tracks play *state* (saves, achievements) but not a diary of *when* you played, across media types.

- **RomM's exact filesystem root/folder-naming convention** (e.g., whether it's strictly `roms/<platform>/` or configurable at a different level pre-5.3.0) wasn't confirmed from a docs page whose content actually rendered — the Quick-Start-Guide fetch returned only a redirect stub.
