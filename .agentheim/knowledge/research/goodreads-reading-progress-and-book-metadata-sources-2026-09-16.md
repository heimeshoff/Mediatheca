# Research: Goodreads reading progress + book metadata sources

## Question
For a new "Books" feature (search modal with cover art, details page, reading-progress tracking from a Goodreads "currently reading" shelf, refreshed on a cadence):

1. Is the official Goodreads API dead in 2026, and is there a replacement?
2. Can reading progress be read without the API (RSS, user-status pages, CSV export), and how do existing OSS projects do it?
3. What are viable book-search/metadata sources for a search modal (Google Books, Open Library, Hardcover, ISBNdb, StoryGraph)?
4. How reliably can a Goodreads shelf item be matched to Google Books / Open Library records?

## Summary

- **The official Goodreads API is dead and has no replacement.** Goodreads stopped issuing new developer keys on **December 8, 2020** and announced it would retire the existing API; this is stated on Goodreads' own `goodreads.com/api` page and cross-confirmed by contemporaneous press coverage [1][2][3]. There is no successor API from Goodreads/Amazon as of 2026 — every source found (including current, actively-maintained GitHub projects) treats the API as permanently gone. **One stale counter-example**: the `goodreads-box` repo's README still instructs users to get a key from `goodreads.com/api/keys` [10] — this is almost certainly an unmaintained/outdated README, not evidence the API works; do not rely on it without live-testing, and no other 2024-2026 source corroborates working keys.
- **CORRECTED (was wrong in an earlier draft): Goodreads reading *progress* IS exposed, publicly and without a cookie, via a separate, undocumented feed.** The shelf RSS feed (`review/list_rss/{user_id}?shelf=currently-reading`) still does **not** carry a progress field — confirmed by a live re-fetch on 2026-09-16 whose full element list has no percent/page field [29]. But `https://www.goodreads.com/user_status/list/{user-id}?format=rss` is a **live, public, key-free, cookie-free feed** that does carry numeric progress: a fetch against a public profile on 2026-09-16 returned 28 items including *"X is on page 137 of 248 of Such Lovely Neighbors"* and *"X is 3% done with Undermoney"* verbatim [28], and two independently-maintained 2026 GitHub projects consume this exact feed with no key/token/cookie at all [31][32]. An earlier draft also misattributed a "Goodreads staff confirmed no progress field" quote — that sentence was written by the *requesting user*, not Goodreads staff (see §2a) — and misread a 2011 "capped at 3" remark (about profile-page *display*, not this feed) as evidence the feed itself was unreliable (see §2b) [33].
- **This new feed's fine print**: it is undocumented by Goodreads, requires the user's profile/status updates to be public, mixes true progress items with non-progress "status" noise that must be filtered by text-pattern matching (no structured percent/page field, just natural-language text), and carries only a book *title* and a status id — no book id or ISBN — so joining a status item back to a shelf item pulled from `review/list_rss/{id}?shelf=currently-reading` (which does carry `book_id`/`isbn`) requires **title-matching**, not a shared key [28][29].
- **The shelf RSS feed itself does still work in 2026 for public profiles**, requires **no key and no auth**, and returns per-book: Goodreads book id, title, author, ISBN, average rating, the user's own 1–5 star rating, cover image URL, publication year, page count, shelf names, and date-added/date-read timestamps — but capped at the **last 100 items per shelf** [4][6][11]. This is corroborated by two independent sources (a personal blog and a Go client library) describing matching field sets [6][11], though exact field-name spelling should be verified against a live feed before implementation.
- **The CSV "Export Library" feature** (My Books → Import and Export → Export Library) is confirmed by three independent how-to sources to **not include reading progress** — its columns are bibliographic/review metadata (Title, Author, ISBN13, My Rating, Average Rating, Publisher, Year Published, Date Read, Date Added, Bookshelves, My Review, Private Notes) [7]. It **requires an authenticated browser session** to trigger (button under My Books) and is rate-limited to roughly once every few days [7] — it cannot be triggered headlessly/unattended, and per **ADR-0070 doctrine this rules it out** as a server-side automation source unless the user manually re-uploads it periodically (a "pasteable export file," which is doctrine-compliant, but not a low-friction refresh cadence).
- **Goodreads has an active anti-automation posture** (Cloudflare/DataDome-class bot detection) as of 2025-2026 per scraping-industry write-ups [8] — none of this is Goodreads' own statement (single-source, vendor/scraper-blog claims), but it is consistent with the complete absence of any 2025-2026 project doing reliable *unauthenticated* progress scraping at scale.
- **Practical implication for Mediatheca under ADR-0070 — CORRECTED, a third option exists.** An earlier draft concluded there was no way to get numeric progress without (a) manual entry or (b) a captured session cookie. That was wrong: **Goodreads' undocumented, public, key-free, cookie-free `user_status/list/{user-id}?format=rss` feed carries numeric progress** ("page N of M" / "N% done") for any user with a public profile [28][31][32], and is doctrine-clean under ADR-0070 (no login, no key, no cookie — a plain unauthenticated HTTP GET). The recommended design: poll this feed on a cadence, filter items to those matching the "is on page N of M of TITLE" / "is N% done with TITLE" text patterns (discarding non-progress status noise like app announcements), and **title-match** the resulting book name back to the shelf item pulled from `review/list_rss/{id}?shelf=currently-reading` (no shared id exists between the two feeds) [28][29]. Caveats to design around: (1) it is entirely undocumented by Goodreads and unsupported — it could change or vanish without notice, so a manual-entry fallback is still needed; (2) it depends on the user's profile/status updates being public; (3) it's natural-language text, not a structured field, so parsing is brittle to phrasing/locale changes; (4) it only has data if the user actually posts status updates on Goodreads (not everyone does when moving a progress slider); (5) title-matching across two unlinked feeds needs the same fuzzy-match caveats as ISBN-less matching elsewhere in this report. The previously-flagged session-cookie route remains available as a doctrine-gray-zone fallback if this feed proves too unreliable in practice, and **user-entered progress in Mediatheca** remains the correct last-resort fallback regardless. Shelf RSS (bibliographic data + shelf membership, no progress) and CSV export (manual, no progress) remain useful for what a book *is* and *whether it's currently being read*, independent of the progress question.
- **For the search modal / metadata**, **Google Books API** and **Open Library** are both good, key-optional-or-free choices; **Hardcover.app** is the most Goodreads-like *replacement with progress tracking* (GraphQL, has `user_books`/`user_book_reads.progress_pages`) but requires the user to have and link a **Hardcover account with an API token** — doctrine-compliant (pasteable token, no password), and worth strongly considering as the actual progress source instead of Goodreads. **StoryGraph has no public API** (confirmed, single vendor roadmap statement that it's "eventually" planned) [13]. **ISBNdb** is a paid metadata API with no progress-tracking concept at all — pure catalog lookup [14].
- **Matching a Goodreads shelf item to Open Library is well-supported**: Open Library edition records expose a `goodreads` array under `identifiers` on the edition JSON (e.g. `/books/{OLID}.json` → `identifiers.goodreads: ["54855"]`) [9] — but this is a **reverse lookup** (Open Library knows about a Goodreads id it was tagged with), not something you can query by Goodreads-id directly at scale; **ISBN is the practical join key** in both directions (Goodreads shelf items carry ISBN/ISBN13; both Google Books and Open Library support direct ISBN search).

## Findings

### 1. State of the official Goodreads API in 2026

Goodreads' own developer page (`goodreads.com/api`) and the pinned/linked Goodreads Developers group state: **"As of December 8th 2020, Goodreads no longer issues new developer keys for our public developer API and plans to retire the current version of these tools."** [1] This is Goodreads' own wording (the WebFetch of `goodreads.com/api` itself only returned generic homepage chrome for me — likely because the API sub-page now redirects or is JS-rendered — so I'm relying on this exact quote as reproduced verbatim across multiple independent tertiary sources including a GitHub issue thread and search-engine synthesis of the live page [1][3]; treat the exact quote as high-confidence but not independently re-verified by me against the raw HTML).

Independent, contemporaneous press corroborates the same date and mechanics: Slashdot (Dec 17, 2020) and multiple tech blogs reported Goodreads "retiring its current API," with the twin actions of (a) no new keys issued from Dec 8, 2020, and (b) any key inactive 30+ days getting deactivated [2][3]. A developer's personal post from the time ("Goodreads shutters all APIs, breaking my open source app") corroborates real-world impact — her existing app broke [2].

**No official replacement API exists.** No source — official or third-party — found in 2026 describes any Goodreads- or Amazon-provided successor API. Every currently-maintained OSS project found (Go RSS client [11], Python CSV converters [7][15], markdown-export tools) explicitly routes around the dead API via RSS, CSV export, or manual data, and states as much in their own docs, e.g., a 2026-era Go package's own docstring: *"The official API was retired in December 2020 and issues no new keys; the feed needs neither key nor auth for a public profile."* [11]

**Single-source caution**: the `goodreads-box` project's README instructs setting up `GOODREADS_API_KEY` from `goodreads.com/api/keys` [10]. This is the one piece of evidence suggesting a key mechanism still nominally exists in the UI, but no source claims new keys are actually issued or that old keys still authenticate against working endpoints in 2026 — most likely this is an unmaintained README written before Dec 2020. **Do not treat this as evidence the API works.**

### 2. Goodreads reading progress without the API

**(a) Shelf RSS feed.** `https://www.goodreads.com/review/list_rss/{user_id}?shelf=currently-reading` (optionally with `&key=...`, though a 2026-era client library states the feed **"needs neither key nor auth for a public profile"** [11]) still works in 2026 for public profiles. A live re-fetch on 2026-09-16 confirms the item shape directly: `guid`, `pubDate`, `title`, `link` (→ `review/show/{review_id}?utm_medium=api`), `book_id`, `book_image_url`/`book_small_image_url`/`book_medium_image_url`/`book_large_image_url`, `book_description`, `num_pages`, `author_name`, `isbn`, `user_name`, `user_rating`, `user_read_at`, `user_date_added`, `user_date_created`, `user_shelves`, `user_review`, `average_rating`, `book_published`, `description` — no goodreads-namespaced elements beyond these plain tag names [29]. This is consistent with, and more complete than, the two prior secondary descriptions of its fields [6][11]. It is **capped at the last 100 items** added to a shelf — confirmed by a Goodreads Developers forum thread on "shelf RSS feed behavior for shelfsize > 100" [4]. **No progress field exists in this feed** — independently confirmed by the live element list above, which contains nothing percent- or page-related [29].
  - **Correction to an earlier draft of this report**: a Goodreads Developers feature-request thread titled "Add reading progress and spoiler flag to shelf RSS feed" was previously mis-cited as containing "a Goodreads-side reply" stating, of progress, *"when I looked in the RSS feed, this statistic is not available."* A live re-read of the thread shows that sentence was written by **the requesting user, Kara Babcock**, describing her own observation — not by Goodreads staff. The Goodreads staffer who did reply, Michael Economy, said only: *"I'm not sure that an rss feed is the best place for this. Have you taken a look at the goodreads api?"* — he neither confirmed nor denied the limitation himself, and the feature was never shipped [5][33]. The underlying fact (no progress field in the shelf RSS) still holds, but on the strength of the independent live-feed verification above [29], not a first-party Goodreads confirmation as previously claimed.

**(b) User-status / reading-progress updates — CORRECTED: this feed does work, publicly, without a cookie.** An earlier draft of this report concluded no working unauthenticated feed existed for `UserStatus` progress. That conclusion was wrong. `https://www.goodreads.com/user_status/list/{user-id}?format=rss` (also reachable in the form `user_status/list/{id}-{name}?format=rss`) is a **live, undocumented but public feed** [30]. A direct fetch on 2026-09-16 against a public profile (id 1), with no login and no cookie, returned 28 items, including numeric-progress entries verbatim: *"X is on page 137 of 248 of Such Lovely Neighbors"* and *"X is 3% done with Undermoney"* [28].
  - **Item shape**: `<title>` carries the human-readable status text — this is where the progress pattern lives (`"is on page N of M of TITLE"` or `"is N% done with TITLE"`); `<description>` is usually empty for progress updates but carries free text for non-progress "updated their status" announcement-style items; plus `<pubDate>`, `<guid>`, and `<link>` pointing to `user_status/show/{status_id}` — a **status id, not a book id**. No goodreads-namespaced elements, no ISBN, no cover URL, and critically **no book id anywhere in the item** — the book is identifiable only by its title as embedded in the status text [28].
  - **Joining back to a shelf item**: since the shelf RSS feed (§2a) carries `book_id`/`isbn`/`author_name` but the status feed carries only a title string, the two feeds share no common key. An implementer must **title-match** the book name parsed out of the status text against the shelf feed's `title` field (with the usual fuzzy-matching caveats for subtitle/edition variance) [28][29].
  - **Noise filtering needed**: the feed mixes true progress items with non-progress status updates (plain "updated their status" entries, app-announcement text unrelated to any book) — an implementer needs to pattern-match the title text against the "on page N of M of TITLE" / "N% done with TITLE" shapes and discard anything that doesn't match. A "finished reading TITLE" pattern is plausible via the same mechanism but was not directly observed in the sampled items and should be treated as unconfirmed pending a dedicated check.
  - **Pagination**: the feed supports a `page=N` query parameter per a 2020 reply in the Goodreads Developers `user_status` thread [33]; this fetch did not paginate past the first page's 28 items, so its practical depth/freshness over a longer history is not yet confirmed and would need a direct `&page=2` check.
  - **Correction on the "3 per person" cap**: an earlier draft cited a 2011 Goodreads-staff remark ("capping at 3 books per person") as evidence the feed was unreliable even historically. A live re-read of that thread shows the remark, from Michael Economy, was about **display on the user's profile page**, and his own message in the same thread states the XML feed shows the same data as the web page — it was not a statement about an RSS/API item cap [33]. A 2026 fetch returning 28 items (far more than 3), plus the existence of `page=N` pagination, corroborates that this feed was never capped the way the earlier draft implied.
  - **Independent corroboration it needs no key/token/cookie**: two independently-maintained 2026 open-source projects consume this exact feed with zero authentication. `sadmanca/astro-loader-goodreads`, a maintained Astro content loader, documents a `UserStatus` schema with a `percentRead` field and states no API key, token, or cookie is required (it separately notes a different, narrower "user updates" feed variant it also supports is capped at the last 10 updates — not to be confused with `user_status/list`) [31]. `kylegoetz/goodreads-rss`, an independent scraper of the same public feed, was built explicitly because "the Goodreads API is very limited," with no authentication of any kind [32]. **This directly contradicts an earlier draft's claim** that "no open-source project demonstrates a currently-working, public, cookie-free path to numeric reading progress in 2026" — two such projects exist.
  - Session-cookie-requiring projects previously cited (e.g. `YashTotale/goodreads-user-scraper` [17]) still apply to non-public-profile data, but are no longer the only path to numeric progress: for public profiles, `user_status/list/{id}?format=rss` needs no cookie. The Home Assistant community thread previously cited [18] is unaffected by this correction — it remains about static "quotes," not progress, and is unrelated to the user-status feed.

**(c) CSV Export Library.** Confirmed by three independent current (2026-dated) how-to guides that the export is triggered manually: My Books → "Import and Export" (left sidebar) → "Export Library" button, generating a downloadable CSV within roughly a minute, rate-limited to once every few days [7]. Columns converge across sources on: Title, Author, ISBN13, My Rating, Average Rating, Publisher, Year Published, Date Read, Date Added, Bookshelves, My Review, Private Notes [7] — **no progress column**, confirming your hypothesis. It **requires an authenticated interactive browser session** (it's a button inside the logged-in "My Books" UI); no source describes a way to trigger it without a live browser session, so it cannot be automated server-side without impersonating a login — which ADR-0070 rules out. It is, however, exactly the kind of **"exported file" ADR-0070 explicitly permits**: the user can manually download and paste/upload the CSV into Mediatheca periodically.

**Anti-scraping posture.** Multiple 2026-dated scraping-industry blog posts (ScrapeOps, DEV Community "How to Scrape Goodreads in 2026," webclaw) describe Goodreads as protected by Cloudflare/DataDome-class bot detection producing immediate 403s for naive scripts, with recommended workarounds (rate limiting 1-3s between requests, header/UA rotation) [8]. **These are all vendor/scraper-blog sources with a commercial interest in making scraping sound both necessary and hard — treat as marketing-adjacent and single-genre-sourced, not confirmed by Goodreads itself.** No official Goodreads Terms-of-Service text on scraping was directly fetched in this research pass (worth a follow-up if scraping is ever seriously considered, though ADR-0070 likely makes this moot for anything requiring login).

### 3. Book search/metadata alternatives for a search modal

**Google Books API**
- Base URL: `https://www.googleapis.com/books/v1/volumes` [19].
- Search: `q` parameter, full-text with special prefixes `intitle:`, `inauthor:`, `isbn:` (e.g. `q=isbn:9780141439600`) [19].
- Auth: **CORRECTED — a key (or an OAuth 2.0 token) is required, not optional, even for public volume data.** An earlier draft called the key "optional," reconciling only the Volumes reference page's "no user authorization required" language. A live re-fetch of Google's own "Using the API" guide on 2026-09-16 is explicit: *"If the request doesn't require authorization (such as a request for public data), then the application must provide either the API key or an OAuth 2.0 token, or both"* [34]. So "no authorization required" means no OAuth *user login* is needed for public volume data — it does not mean no credential at all; a `key=yourAPIKey` query parameter (or a bearer token) must still be supplied on every request.
- Quota: official docs page fetched did not state a number; secondary sources disagree — one claims ~1000/day historically, another claims 10,000/day as of late 2023/2024 for keyed requests [20]. **This is a single/conflicting-source point — verify current quota against the Google Cloud Console for your own key before relying on volume.** Unkeyed quota is lower but not quantified in any source found.
- Cover art: `volumeInfo.imageLinks` object with `smallThumbnail`, `thumbnail`, `small`, `medium`, `large`, `extraLarge` URLs [19] — good fit for both a search-modal thumbnail and a details-page hero image.
- ISBN matching: direct `isbn:` query term, and volumes include `industryIdentifiers` (ISBN_10/ISBN_13) in results, making it a solid join target for a Goodreads-shelf ISBN.

**Open Library**
- Search: `https://openlibrary.org/search.json?q=...` (general query; ISBN can be searched as `q=isbn:{isbn}` or via `fields`/`isbn` query-style terms), with an explicit `fields` parameter to limit response size, warned as "expensive... please use sparingly" if `*` (all fields) is requested [21].
- Dedicated ISBN lookup: `https://openlibrary.org/isbn/{isbn}.json` returns edition-level metadata directly [22].
- Covers: `https://covers.openlibrary.org/b/$key/$value-$size.jpg` where `$key` ∈ {ISBN, OLID, OCLC, LCCN, "id"/CoverID} and `$size` ∈ {S, M, L} [23].
- Auth: **no key required.** Rate limits: default **1 req/sec** for unidentified requests, **3 req/sec** if you send a descriptive `User-Agent` header with app name + contact email ("identified" requests) [24]. The **covers** subdomain has a separate, stricter limit: **100 requests per IP per 5 minutes** for lookups by ID types other than CoverID/OLID, returning 403 if exceeded [23][24]. Bulk/high-volume use is explicitly discouraged in favor of downloading Open Library's data dumps [21].
- Goodreads-id linkage: **confirmed** — edition JSON (`/books/{OLID}.json` or via `/isbn/{isbn}.json`) includes an `identifiers` object that can contain `identifiers.goodreads: ["<id>", ...]` when a librarian/contributor has added it, e.g. `identifiers: { goodreads: ["54855"], librarything: ["3414"] }` [9]. This is **not guaranteed present on every edition** (it's crowd-contributed metadata), so treat it as a bonus join, not a primary one — ISBN remains the reliable join key in the Goodreads→OpenLibrary direction; the reverse (Goodreads-id→OpenLibrary lookup) has no dedicated query-by-goodreads-id endpoint found, so you would need to search Open Library's dataset/dumps offline if you needed that direction at scale, or just rely on ISBN.

**Hardcover.app**
- Endpoint: GraphQL at `https://api.hardcover.app/v1/graphql` [25]. Auth via `Authorization: Bearer <token>` where the token is generated by the user in their own Hardcover account settings ("Hardcover API" link → "New API Key") [25] — this is a **pasteable personal access token from an account the user owns**, not a Goodreads-style third-party login on Mediatheca's behalf, so it is compatible with ADR-0070's doctrine as I understand it (the "login" being performed is the *user's own*, on Hardcover's own site, generating a token they hand to Mediatheca — same shape as the TMDB/Steam key patterns already in the codebase).
- Progress: `user_books(where: { status_id: { _eq: 2 } })` (status 2 = "Currently Reading" per a documented status_id enum: 1 Want to Read, 2 Currently Reading, 3 Read, 4 Paused, 5 Did Not Finish) with nested `user_book_reads { progress_pages }` and `book { title pages image { url } contributions { author { name } } }` — a concrete example query returning per-book page-level progress was reproduced from a community source describing the API [26]. **This single community example is the only concrete query I found**; the endpoint URL, auth mechanism, and status_id enum are corroborated by Hardcover's own docs page structure, but the exact GraphQL query shown should be validated against Hardcover's live schema/docs before implementation (a direct WebFetch of `docs.hardcover.app/api/getting-started/` returned HTTP 403 during this research pass, so their docs could not be independently re-verified here — treat field names as plausible but unconfirmed pending a follow-up fetch, e.g. via `curl` or a logged-in browser).
- Rate limits: one community source states 60 requests/min, 30s timeout, max query depth 3 [26] — single-source, unverified against official docs due to the 403 above.
- **Assessment**: Hardcover is the most Goodreads-like replacement *with actual progress tracking*, and if the user is willing to also use Hardcover to track "currently reading," it directly solves the progress-tracking half of this feature far better than anything Goodreads-side can offer in 2026. Requires the user to adopt a second service, though.

**ISBNdb** — ⚠️ **UNVERIFIED PRICING.** A direct re-fetch of `isbndb.com/isbn-database` in this correction pass again returned HTTP 403 (as it did in the original pass), so its tier prices and quotas could not be independently verified against ISBNdb's own site in either pass — they rest entirely on a third-party aggregator (api.market), and secondary sources disagree on the mid tiers (some report $35.99/month for 15,000 searches and a $74.95 "Pro" tier, others a ~$5/month academic tier, versus the $14.99–$299.99 range and $2,000/day academic figure given below) [27]. Treat every ISBNdb pricing figure here as unverified and confirm against the live pricing page (e.g., via an authenticated browser session) before relying on it: paid, tiered, roughly $14.99–$299.99+/month for 5,000–50,000+ daily searches, with a cheaper academic tier around 2,000/day per the aggregator source [27]. Pure metadata (ISBN10/13, title, author, pub date, publisher, binding, pages, price, cover thumbnail, language, edition, format, synopsis, subject, weight, dimensions — "up to 19 data points") [27], bulk lookup (100–1000 ISBNs/request depending on tier) [27]. No progress-tracking concept at all — a pure catalog API, worth considering only if Google Books/Open Library coverage proves insufficient for older/niche titles, and it costs money where the other two are free.

**StoryGraph** — **confirmed no public API.** StoryGraph's own product-roadmap post states an API is a distinct, "eventually" planned feature, separate from existing partner integrations (e.g. Kobo) [13]. This is a single first-party source (StoryGraph's roadmap/Threads post) but it's a direct company statement, so reasonably reliable. Existing "storygraph-api" GitHub projects are all screen-scrapers of the user's own profile requiring a `remember_user_token` cookie [13] — same session-cookie caveat as Goodreads scraping, and same ADR-0070 gray-zone flag applies if ever considered.

### 4. Matching strategy: Goodreads shelf item → Google Books / Open Library

Given a Goodreads shelf item's `{book_id, isbn/isbn13, title, author}` (available from the RSS feed per §2a):

- **ISBN is the reliable join key in both directions.** Google Books supports direct `isbn:` search terms against `volumes` and returns `industryIdentifiers` for confirmation [19]. Open Library supports both `search.json?q=isbn:{isbn}` and a dedicated `/isbn/{isbn}.json` edition endpoint [21][22]. Since Goodreads shelf RSS items carry ISBN/ISBN13 directly [6][11], a straightforward ISBN-first lookup against either service should resolve the large majority of mainstream titles; title+author fallback (fuzzy match) would be needed for items lacking an ISBN (e.g., some editions, omnibus/anthology entries) — no source quantifies a real-world match-rate percentage for this, so **treat "large majority" as a plausible but unverified estimate**, not a cited figure.
- **Goodreads-id ↔ Open Library mapping exists but is one-directional and incomplete.** Open Library edition records can carry a crowd-contributed `identifiers.goodreads` array (confirmed via a concrete example: `identifiers: { goodreads: ["54855"], librarything: ["3414"] }` on an edition JSON) [9]. This means if Open Library already has your specific edition tagged with its Goodreads id, you could in principle build a local `goodreads_id → OLID` table by walking Open Library's data (dumps, since there's no "search by goodreads id" query endpoint), but for a live matching workflow **ISBN lookup is simpler and equally reliable**, and doesn't depend on whether a librarian happened to add the cross-reference.
- Google Books has no documented Goodreads-id field; matching there is ISBN- or title/author-only.

## Open questions

- **Exact Google Books quota numbers (keyed vs unkeyed)** are unresolved — sources disagree (1,000/day vs 10,000/day); needs a direct check of Google Cloud Console quota pages for a real project, or a fresh fetch of the current quota-specific Google doc page (not just the "Using the API" page).
- **Hardcover's official docs could not be fetched directly (403)** — the GraphQL query shape, exact rate limits (60/min, depth 3, 30s timeout), and the `status_id` enum values used in this report come from a single community source, not Hardcover's own docs. Recommend a follow-up fetch (e.g. via `curl`/authenticated browser, since WebFetch was blocked) before committing to a schema in code.
- **No source directly confirms Goodreads' Terms of Service text on scraping** in 2026 — only third-party scraping-industry commentary was found. If any Goodreads-facing automation beyond the public RSS feed is ever considered, fetching the actual current ToS is a prerequisite.
- **Whether a Goodreads *session cookie* (as opposed to a password) falls inside or outside ADR-0070's doctrine** is a judgment call for the architect/ADR owner, not something this research can resolve — flagged prominently in the Summary for that decision to be made explicitly rather than by default. This is now a secondary fallback question rather than the primary design decision, since the public `user_status` feed is doctrine-clean and should be tried first.
- **`user_status/list/{id}?format=rss` depth beyond page 1 is unconfirmed** — a single fetch returned 28 items with no explicit pagination metadata in the feed body itself, and a `page=N` parameter is documented only by a 2020 forum reply, not by Goodreads. A follow-up fetch of `&page=2` (and beyond) against a profile with a long status history would confirm real depth, staleness, and whether item count/order is stable across requests.
- **Whether a "finished reading TITLE" status pattern exists in this feed** was not directly observed in the sampled items (only "on page N of M" and "N% done" were seen) — worth confirming with a larger/targeted sample before building a parser that assumes it.
- **Real-world title-match reliability between a `user_status` item's embedded book title and the corresponding `review/list_rss` shelf item's `title` field** is unquantified — since the two feeds share no id, this join's success rate (subtitle/edition/translation variance) should be spot-checked against a real reading list before committing to it as the sole join strategy.
- **ISBNdb's actual current pricing** could not be verified against `isbndb.com/isbn-database` directly (HTTP 403 on repeated attempts) — all figures in §3 rest on a third-party aggregator and are flagged ⚠️ UNVERIFIED; a follow-up via an authenticated browser or a cached/alternate source is needed before quoting a price to a decision-maker.
- **Real-world ISBN match-rate between a typical Goodreads shelf and Google Books/Open Library** is not quantified in any source — this report's "large majority" claim is an inference, not a cited statistic.
