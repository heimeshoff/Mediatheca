Mediatheca — Data Architecture

Where every piece of information lives in mediatheca.db (plus the images/ file cache): what is the event-sourced source of truth, what is projected from it, what is cached from external systems, and what exists nowhere else. Every table's tier is formally declared in Administration.fs:390–462 (tableRegistry) as Projected / Cache / Imperative.

1 · Event store — the source of truth

A single append-only events table (EventStore.fs:52–76): global_position (store-wide order, gaps legal by design), stream_id, stream_position (optimistic-concurrency key via UNIQUE(stream_id, stream_position)), event_type, JSON data/metadata, ISO-8601 timestamp. An FTS5 index (events_fts) mirrors data for the admin event-log search. projection_checkpoints tracks each projection's last_position.

  • Writers: the generic command handler (Api.fs:66–98), admin compensating events, the nightly Steam playtime sync (PlaytimeTracker.fs:113), the nightly TMDB series refresh (SeriesRefresh.fs:289,360), and the startup-cutover automation.
  • Projections are effectively synchronous: every append is immediately followed by a catch-up of all registered handlers in the same request (Api.fs:96–97) — read models never lag in normal operation.
  • Rebuild machinery: per-projection drop-and-replay via SSE admin route; event surgery (edit/delete/rename) rewinds all checkpoints to 0 and forces rebuilds; a shadow-replay drift detector diffs live tables against a fresh in-memory replay (ADR-0031).
  • Not event-sourced by explicit decision: the game journal (migrated out of the event store), settings, cast/crew, all caches, job runs.

3 · Cache tier — external data, never replayed

Re-derivable from external systems. Never checkpointed, never drift-checked, deliberately excluded from projection dropTables. The hard rule (ADR-0045, MetadataCache.fs:20–30): no projection handler may read this tier — violated in one place (see hazards).

6 · Rebuild-integrity hazards

Not duplication, but places where the "projections are disposable" guarantee is weaker than it looks.

H1 — SeriesProjection reads the cache tier during replay (the one real violation) The Season_marked_watched handler expands a season into per-episode progress rows by querying series_episode_cache inside handleEvent (SeriesProjection.fs:546–552) — exactly what ADR-0045 and the file's own comments forbid. Consequences: a rebuild against an empty or stale episode cache silently writes wrong progress rows (and a wrong watched_episode_count), and the ADR-0031 shadow-replay drift detector replays into a throwaway connection that has no episode cache at all, so this arm is a latent no-op there. Fix: enrich the event at command time (record the concrete episode numbers in the payload, as Episodes_watched_up_to already does).
H2 — FriendProjection writes into MovieProjection's tables, and only Movie's Friend_removed scrubs the removed slug from movie_detail and watch_sessions (FriendProjection.fs:84–138) but not from the equivalent series (series_detail, series_rewatch_sessions) or game (game_detail) blobs — removed friends linger there. It also couples rebuild order: rebuilding MovieProjection alone resurrects deleted friend slugs until FriendProjection replays again (registration order is documented as load-bearing for this reason). Either scrub all three contexts symmetrically or, cleaner, filter deleted friends at read time in resolveFriendRefs and drop the cross-projection write entirely.
H3 — A read that writes SeriesProjection.getBySlug inserts a missing default rewatch-session row during a read (SeriesProjection.fs:962–976). Self-healing, but it means query traffic mutates projection state outside replay — invisible to the drift detector's model.

7 · What actually needs backing up

Ranked by irreplaceability. The event store plus these is the true backup surface; everything else regenerates.

Irreplaceable (no upstream source)

  • events — the entire user history of six contexts
  • game_journal_blocks — original writing, replaced wholesale on every save, no history
  • settings — credentials + tokens (only 4 API keys re-seed from env vars)
  • images/friends/ and images/content/ — user uploads

Expensive or partial to regenerate

  • movie_cast / series_cast / cast_members — no refresh path at all; only crew self-heals at boot
  • Movie/game posters, backdrops, cast portraits — write-once downloads, never re-fetched
  • series_*_cache + series_metadata_cache — nightly refresh restores only airing / recently-watched series
  • game_metadata_cache descriptions + HLTB hours — manual re-fetch only

Fully self-healing

  • All 14 projected tables — drop + replay
  • jellyfin_movie/series/episode — one sync
  • movie_crew — startup backfill
  • movie_metadata_cache — empty stub

Disposable

  • job_runs — observability only (but unbounded growth: consider retention pruning)
  • events_fts — rebuilt from events
  • projection_checkpoints — rewound to 0 and replayed
