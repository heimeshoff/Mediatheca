Mediatheca — data flow architecture

How information moves from write-side events to the frontend, grouped by bounded context. Generated from the source under src/Server/ and src/Shared/Shared.fs.

Pattern A · Full CQRS

Append-only events → SQL projection (read model) → query → frontend. Used by every domain aggregate.

Pattern B · Event log as view

Frontend reads the raw events table directly. No projection step.

Pattern C · Database as source of truth

Plain CRUD against a SQL table or filesystem. Never event-sourced.

At a glance

SQLite holds three different things: an append-only events table, a set of projected read-model tables, and a set of plain CRUD tables. Every domain mutation runs through Api.executeCommand: read stream → reconstitute aggregate → decide → append → catch up projections.

Event-sourced (Pattern A)

  • Movies — Movie-{slug}
  • Friends — Friend-{slug}
  • Series — Series-{slug}
  • Games — Game-{slug}
  • Catalogs — Catalog-{slug}
  • Content blocks — ContentBlocks-{movie}

Event log views (Pattern B)

  • Event Browser page
  • Dashboard “Recent Activity” widget

DB-direct (Pattern C)

  • Settings (SettingsStore)
  • Cast / crew (CastStore)
  • Jellyfin mappings (JellyfinStore)
  • Steam playtime (PlaytimeTracker)
  • Image files (ImageStore, filesystem)

Pattern A · Event-sourced bounded contexts

Every aggregate follows the same shape — events are appended to events (one stream per aggregate id), Projection.runProjection reads from a checkpoint and updates the read-model tables, and the Fable.Remoting API queries those tables. The frontend never sees raw events on these flows.

Pattern C · Database as source of truth

Some data is genuinely not domain-event material — it's either external metadata (cast lists, Jellyfin item IDs), user configuration (API keys), or high-frequency telemetry (Steam playtime snapshots). These stores live in their own SQLite tables and never go through the event log.

Cross-cutting notes

Command path. Every write goes through Api.executeCommand in src/Server/Api.fs: it reads the stream with EventStore.readStream, reconstitutes state via evolve, calls decide, appends new events with optimistic-concurrency, then calls Projection.runProjection for each handler so read models stay in sync before the response returns.

Boot sequence (Program.fs). Tables are created, SeriesProjection and GameProjection are rebuilt from zero, then all six projections run a catch-up pass. CastStore, JellyfinStore, PlaytimeTracker, SettingsStore initialise their own (non-event-sourced) tables on the side.

Dashboard. It's the most mixed page — most widgets hit the read-model tables (movie_detail, watch_sessions, game_play_session), but the Recent Activity widget reads raw events.
